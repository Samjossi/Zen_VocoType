## 1. 背景与约束

本文档落地 [`work charter/2026-0721-0529_GridChat迁移Zen_VocoType重写大纲.md`](../work%20charter/2026-0721-0529_GridChat迁移Zen_VocoType重写大纲.md) §6 阶段 3 的实现层技术决策。阶段 1/2 已交付 Service（先监听后异步加载、`health`/`ready` 协议接口、PID 文件）与 Client（服务端缺席明确提示），Launcher 的全部设计建立在这两个组件的协议能力之上。

**硬性约束**（源自大纲 §2、§5 与 §6 阶段 3 验收标准，选型不得违反）：

| # | 约束 |
|:---|:---|
| C1 | 协议级就绪信号：等待「模型已就绪」必须走 `ready` 接口轮询，🔴 禁止固定 sleep 充当同步（根除旧 0.5s/4s/60s 魔法数字） |
| C2 | 超时预算基于 P99 冷启动实测；必须区分「进程已死」与「仍在启动」；🔴 禁止超时即失败一刀切 |
| C3 | 失败可清理：任何启动/等待失败必须回收已拉起的子进程，不留孤儿进程 |
| C4 | 🔴 禁止 `pkill -f "python main.py"` 粗暴停服；禁止 psutil 子串匹配查进程——PID 文件 + 可执行路径精确匹配 |
| C5 | 单实例锁：重复执行幂等（已运行时明确提示并退出，不产生第二套进程） |
| C6 | exit code 必须真实反映成败（根除旧版恒为 0 的缺陷） |
| C7 | `--dev` 模式：用当前 `.venv` 的 `python main.py` 拉起两端源码，使用契约库 `paths.DEV_SOCKET_PATH` 独立 Socket 与正式版隔离；两种模式行为一致、互不干扰 |
| C8 | 路径自定位：正式模式下服务端/客户端二进制路径基于 Launcher 自身目录或显式配置解析，🔴 禁止硬编码个人机器路径与 cwd 相对路径 |
| C9 | 每组件单一配置源（pydantic-settings，阶段 0 选型七既定）；Launcher 骨架与 `config.py` 已就位 |

**已冻结的外部事实**：Service 冷启动 Socket 可连接 ≤ 5 秒（阶段 1 验收），模型异步加载完成时间由 `ready` 接口报告；Client 启动后自行 health 探测，服务端未就绪时客户端托盘明确提示——因此 Launcher 的就绪等待是对用户体验的加强（避免客户端红态闪现），不是客户端正确性的前提。

## 2. 选型一：子进程拉起与生命周期管理

> 背景：Launcher 需拉起 Service 与 Client 两个子进程，并在失败/退出时可靠回收。旧 Launcher 用 psutil 查进程 + `pkill -f` 停服，有误报与竞态（大纲 §5-6/7）。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. `subprocess.Popen` + `start_new_session=True` + 进程组回收 | 标准库零依赖；`Popen` 句柄即精确身份（无查进程环节）；独立会话使 `os.killpg` 可整组回收（孙进程不逃逸）；`poll()` 直接区分「进程已死」与「仍在运行」 | 需自行维护句柄表与回收顺序 |
| B. psutil `Process` 包装 | 进程树遍历、CPU/内存信息现成；`children(recursive=True)` 回收方便 | 本质是 PID 复用风险下的包装；Launcher 依赖已含 psutil 但核心能力 A 均可由标准库完成 |
| C. systemd --user service | 系统级生命周期管理、崩溃自动重启、journal 日志 | 🔴 引入系统级安装步骤，背离「双击即用」形态；桌面入口与 systemd 单元双重维护；v1 过度设计 |

**推荐结论：A 为主，B 仅作诊断辅助**。`Popen` 句柄是唯一身份凭据（根除「查进程」这一整类竞态）；两个子进程各自 `start_new_session=True`，回收时 `os.killpg(pg, SIGTERM)` → 带超时等待 → `SIGKILL` 兜底的两段式终止；psutil 仅用于选型四的既有实例精确识别（按可执行路径匹配），不参与自己拉起的子进程管理。

## 3. 选型二：协议级就绪等待机制

> 背景：C1 要求用 `ready` 接口确认「模型已就绪」。旧事故根因即固定 sleep + 超时一刀切。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. 两阶段条件等待：Socket 可连 → `ready` 轮询 | 阶段一确认进程活着且服务已监听（快路径，阶段 1 验收 ≤5s）；阶段二轮询 `ready` 拿到真实模型就绪状态；每阶段独立超时，语义清晰 | 需实现一个通用「条件等待」helper（带超时的轮询循环，约 30 行） |
| B. 仅轮询 `ready`（连接失败视为未就绪） | 实现最少 | 连接拒绝与模型加载中混为一谈，无法区分「进程已死/端口异常」与「正常加载中」，违反 C2 |
| C. 固定 sleep 后一次性 `ready` 检查 | 最简单 | 🔴 违反 C1，旧方案本身，明确排除 |

**推荐结论：A**。细节：

- 通用 helper `wait_until(predicate, timeout, interval)`：条件满足即返回，超时抛 `TimeoutError`；轮询间隔为命名常量（默认 200ms，注明依据：就绪信号精度要求低，200ms 兼顾响应速度与 Socket 压力）
- 阶段一 `connectable`：尝试建连成功即过；同时并行检查 `Popen.poll()`——子进程已退出则立即失败并读取其退出码与日志尾部（🔴 禁止干等超时）
- 阶段二 `model_ready`：复用同一连接（或短连轮询）调 `ready`；响应未就绪时载荷中携带加载进度/模型名时写入 debug 日志
- 超时常量集中定义于配置：`socket_wait_timeout_s`（默认 15s，依据：阶段 1 验收 ≤5s 的 3 倍余量）、`model_ready_timeout_s`（默认 180s，依据：需在阶段 3 实测 P99 后回填校准，初值覆盖冷机模型加载上限）；两者均可配置，🔴 禁止散落魔法数字

## 4. 选型三：单实例锁实现

> 背景：C5 要求重复执行幂等。锁的载体需选型。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. `fcntl.flock` 锁文件（用户私有运行目录） | 内核级锁，进程死亡（含 SIGKILL）自动释放，🔴 无陈旧锁问题；持锁期间可向文件写入 PID/模式/启动时间供第二次执行读取并提示 | 仅本机有效（对桌面单机场景够用） |
| B. PID 文件存在性 + 进程存活检查 | 实现直观 | 🔴 PID 复用竞态；进程异常死亡留陈旧文件，需额外清理逻辑（旧 Launcher 同款缺陷） |
| C. Unix 抽象 Socket 绑定占用 | 死亡即释放 | 无法附带实例元信息（PID/模式），提示文案信息少；与业务 Socket 路径易混淆 |

**推荐结论：A**。锁文件位于用户私有运行目录（与 Socket 同目录策略，经契约库/配置统一定位，🔴 禁止 `/tmp` 固定路径——多用户冲突且不符合 XDG 规范）；正式模式与 dev 模式使用**不同锁文件**（互不阻塞，满足 C7 互不干扰）；获取失败（`BlockingIOError`）→ 读取锁文件内元信息 → 通知「Zen_VocoType 已在运行（PID xxx，dev/正式模式）」→ 以既定退出码退出（选型七），🔴 禁止拉起第二套进程。

## 5. 选型四：既有实例与冲突进程识别

> 背景：单实例锁管「Launcher 自身」；还需处理「Service/Client 残留进程」（上次异常退出留下的孤儿）与「Socket 路径被外部占用」两类冲突。旧方案 psutil 子串匹配误报（大纲 §5-7）。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. 读 Service/Client 的 PID 文件 + `/proc/<pid>/exe` 可执行路径精确匹配 | 身份精确到可执行文件本身，误报为零；PID 复用时 exe 不匹配即识别为陈旧文件并清理 | 需处理 PID 文件缺失（进程并非由上次正常流程留下）的盲区 |
| B. psutil 全表扫描 + cmdline 精确匹配 | 能发现无 PID 文件的残留 | 扫描成本高；cmdline 匹配规则写窄了漏报、写宽了误报，两难 |
| C. 不识别，直接拉起 | 实现为零 | 🔴 端口/Socket 冲突时行为不可预期，违反 C3 精神 |

**推荐结论：A 为主 + Socket 占用兜底探测**。流程：读 PID 文件 → 存活且 exe 路径与本次目标一致 → 视为「已在运行的合法实例」，正式模式下跳过拉起直接进入就绪等待（幂等）；exe 不匹配或进程已死 → 判定陈旧，删除 PID 文件继续。补充兜底：拉起 Service 前若业务 Socket 路径已存在且可连接，做一次 `health` 探测——是本组件协议则复用/提示，非本组件协议则报错「Socket 路径被外部占用」并退出（🔴 禁止 unlink 他人 Socket）。B 的全表扫描不采用。

## 6. 选型五：失败清理与进程回收策略

> 背景：C3 —— 任一环节失败（Service 拉起失败、就绪超时、Client 拉起失败）必须回收已分配资源。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. 显式资源栈（contextlib.ExitStack / try-finally 分层）+ 进程组终止 | 回收顺序明确（后拉起先回收）；每步注册对应清理动作，异常路径与正常路径同一套代码；可单测（注入假 Popen） | 需仔细设计注册粒度 |
| B. 全局 atexit 钩子统一杀 | 任何退出路径都覆盖 | atexit 不覆盖 SIGKILL/崩溃；与正常「拉起后退出」语义冲突（选型八：正常路径不杀子进程），需额外标志位区分，反而绕 |
| C. 子进程设 `prctl(PR_SET_PDEATHSIG)` | 父死子随 | 仅覆盖「Launcher 死亡」一种场景；不覆盖「就绪超时主动失败」的清理；Linux 特定且需 ctypes |

**推荐结论：A 为主、C 为补充保险**。回收动作按逆序执行：终止进程组（SIGTERM → 5s 命名常量宽限 → SIGKILL）→ 清理本端创建的临时文件；每步回收动作记日志。C 作为 Belt-and-Braces：对两个子进程设置 `PR_SET_PDEATHSIG`，Launcher 意外死亡时子进程收到信号自行退出，杜绝孤儿（Service/Client 侧需约定收到 SIGTERM 优雅退出——阶段 1/2 已实现信号处理，此处复用）。B 的 atexit 方案因与选型八语义冲突不采用。

## 7. 选型六：退出码约定

> 背景：C6 —— 旧 Launcher 返回值约定混乱导致 exit code 恒为 0。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. 语义化退出码枚举（0/2/3/4/5/6） | 每类失败一个码，脚本与桌面环境可区分处理；README 可列排查表 | 需在全部失败分支统一收口（单一 `main() -> int` 返回） |
| B. 0/1 二分 | 简单 | 无法区分「已在运行」（非错误）与「启动失败」，不满足验收的排查需求 |

**推荐结论：A**。初稿：`0` 成功拉起全套（或已在运行的幂等命中并确认就绪）；`2` 已在运行但实例异常（就绪等待失败）；`3` 服务端拉起/就绪失败；`4` 客户端拉起失败；`5` 配置/路径错误（组件缺失等）；`6` 锁冲突外的内部错误。所有失败分支经单一出口返回，🔴 禁止散落的 `sys.exit` 字面量；`main()` 返回值即进程退出码。

## 8. 选型七：Launcher 驻留形态

> 背景：大纲 §3.1 遗留待定项——Launcher 拉起两端后即退出，还是驻留监控子进程。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. 拉起确认就绪后即退出 | 职责单一（编排器而非守护进程）；崩溃零影响运行中的两端；与桌面入口语义一致（双击启动器不应挂一个常驻进程）；第二次执行天然成为「健康检查+幂等」入口 | 子进程崩溃后无自动拉起；用户需手动再执行 |
| B. 驻留监控 + 崩溃自动重启 | 无人值守可用性高 | Launcher 自身成为单点与常驻资源消耗；需设计重启风暴保护；与「Launcher 不参与运行时业务」职责划分冲突；第二实例与驻留实例的锁语义复杂化 |
| C. 可选驻留（`--daemon` 参数） | 两者兼得 | 两条代码路径都要测；v1 范围膨胀 |

**推荐结论：A**。理由：子进程崩溃时客户端托盘已能呈现服务端断连状态（阶段 2 交付），用户再执行一次 Launcher 即恢复——这条路径已被幂等设计覆盖。崩溃自动拉起若有真实需求，属 v2 范畴（届时评估 systemd --user 或驻留模式），本阶段不做。

## 9. 选型八：状态通知方案

> 背景：阶段 3 交付物含 notify-send 状态通知（含通知图标迁移接入）。需定稿调用方式与通知时机。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. `notify-send` 子进程 + 迁移图标 | 桌面原生通知；libnotify 在目标环境普遍存在；图标经自定位 helper 传入（`assets/zen_vocotype_launcher_icon_*.png`） | 依赖 libnotify；通知发送本身可能失败 |
| B. libnotify 库绑定（pygobject） | 无子进程开销 | 引入 gi 依赖——阶段 0 选型一刚因 gi 打包坑弃用 GTK 栈，🔴 自相矛盾 |
| C. 无通知，仅终端输出 | 零依赖 | 双击桌面入口无终端，用户对启动进度完全无感知 |

**推荐结论：A**。通知时机收敛为三类（🔴 禁止每步刷通知）：「正在启动」（拉起 Service 时）、「启动完成」（客户端就绪后，含总耗时）、「启动失败」（含失败阶段与日志位置提示）。`notify-send` 缺席时降级为仅日志 + 退出码，记 warning（🔴 禁止静默降级）；通知发送失败不阻塞主流程但记 warning。图标加载走「程序自身目录」解析 helper（兼容 `_MEIPASS`），缺失记 warning（大纲 §5-13 同款约束）。

## 10. 选型九：`--dev` 开发模式实现

> 背景：C7 —— dev 模式用 `.venv` 拉起两端源码，Socket 与正式版隔离。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. 命令行参数 `--dev` + 模式注入子进程环境 | 单一入口；模式差异收敛为「目标命令 + Socket 路径 + 锁文件」三处替换，其余流程（就绪等待/清理/退出码）完全复用，行为一致性由共享代码保证 | 需在配置层明确模式相关路径的推导规则 |
| B. 独立 `dev_launcher.py` 脚本 | 互不干扰 | 🔴 双份编排逻辑漂移（旧项目脚本重复漂移同款问题），明确排除 |
| C. 配置文件切换（dev.yaml） | 无命令行参数 | 多一个配置源雏形，违反 C9 精神；模式是运行时选择而非配置 |

**推荐结论：A**。模式差异表：

| 项 | 正式模式 | dev 模式 |
|:---|:---|:---|
| Service 命令 | 自定位解析的打包二进制 | `.venv/bin/python -m`（或 `main.py` 绝对路径，自定位解析仓库根） |
| Client 命令 | 同上 | 同上 |
| Socket 路径 | 契约库默认 `SOCKET_PATH` | 契约库 `paths.DEV_SOCKET_PATH`（唯一出处，🔴 禁止 Launcher 自造） |
| 锁文件 | 正式锁文件 | dev 锁文件（选型三） |
| 环境注入 | 默认 | 向子进程注入 Socket 路径覆盖环境变量（pydantic-settings 环境变量覆盖机制，阶段 0 选型七既定） |

`.venv` 与仓库根的定位基于 Launcher 自身位置向上解析（开发目录布局固定），解析失败明确报错（退出码 5）；🔴 禁止 cwd 相对解析。

## 11. 选型十：模块划分与可测性

> 背景：阶段 2 评审落实了「回调只发信号」等架构约束；Launcher 虽无 UI 线程问题，但编排逻辑的失败分支密集，需结构保证可测。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. 按职责拆模块 + 依赖注入（Popen 工厂/等待器/通知器可替换） | 失败分支可单测全覆盖（模拟慢启动/崩溃/超时/锁冲突，正是验收标准要求）；无全局状态 | 模块数较多（但每个都小而直） |
| B. 单文件流程式脚本 | 一眼读完 | 🔴 旧 Launcher 同款形态；失败分支无法隔离测试 |

**推荐结论：A**。初稿模块：`config.py`（已就位）、`locks.py`（单实例锁）、`processes.py`（拉起/进程组回收/PDEATHSIG）、`discovery.py`（PID 文件+exe 精确匹配+Socket 兜底探测）、`readiness.py`（两阶段条件等待，协议客户端复用契约库帧编解码）、`notify.py`（notify-send+图标）、`orchestrator.py`（编排主流程+资源栈清理）、`exit_codes.py`（退出码枚举）、`main.py`（CLI 入口）。`orchestrator` 对 `processes`/`readiness`/`notify` 仅依赖注入的接口，验收要求的「模拟服务端慢启动/崩溃」以 fake 注入方式进入单测，🔴 禁止只能靠手工真机验证。

## 12. 推荐结论汇总

| # | 选型项 | 结论 | 关键理由 |
|:---:|:---|:---|:---|
| 1 | 子进程管理 | **`Popen` + 独立会话 + 进程组两段式回收** | 句柄即身份，根除查进程竞态 |
| 2 | 就绪等待 | **两阶段条件等待（可连 → `ready` 轮询）** | 满足 C1/C2；进程死即时失败 |
| 3 | 单实例锁 | **`flock` 锁文件（正式/dev 分离）** | 死亡自动释放，无陈旧锁 |
| 4 | 进程识别 | **PID 文件 + `/proc/exe` 精确匹配 + Socket 兜底探测** | 零误报；幂等基础 |
| 5 | 失败清理 | **ExitStack 逆序回收 + `PR_SET_PDEATHSIG` 保险** | 满足 C3；杜绝孤儿 |
| 6 | 退出码 | **语义化枚举 + 单一出口** | 满足 C6 |
| 7 | 驻留形态 | **拉起确认后即退出** | 职责单一；幂等重入即健康检查 |
| 8 | 通知 | **notify-send 三类时机 + 迁移图标** | 双击场景有反馈；失败不静默 |
| 9 | dev 模式 | **`--dev` 参数 + 三处差异替换** | 行为一致性由共享代码保证 |
| 10 | 模块结构 | **职责拆分 + 依赖注入** | 慢启动/崩溃场景可单测 |
