## 2. 选型一：客户端 UI / 托盘框架

> 背景：旧客户端用 GTK3 + AppIndicator3，踩坑密集——托盘录音后消失、GTK 线程安全靠 `GLib.idle_add` 打补丁、托盘方案重写过 3~4 次、打包后 gi 模块问题不断。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. GTK3 + AppIndicator3（沿用旧方案重写） | 旧项目线程模型经验可直接继承（主线程 GTK 循环 + `GLib.idle_add` + 信号转发）；系统主题融合好；无额外大依赖 | 旧项目大部分恶性 bug 源于此栈；GTK 线程模型反直觉，所有 UI 操作必须回主线程；AppIndicator 在不同桌面环境表现不一；打包需处理 gi/typelib 系统依赖 |
| B. PySide6（Qt `QSystemTrayIcon`） | 信号槽跨线程安全，线程模型清晰；`QSystemTrayIcon` 经 StatusNotifierItem 协议在现代桌面工作良好；API 文档与社区资源最丰富；后续若加窗口 UI 扩展性好 | 依赖体积大（~150MB+）；LGPL 动态链接合规需注意；托盘菜单定制自由度略低于 GTK |
| C. 无托盘纯后台 + 命令行/通知交互 | 依赖最少；彻底回避托盘兼容性 | 用户无可视化状态与入口，体验倒退；不符合产品交互模型（大纲 §4 继承旧交互模型） |

**综合对比**：

| 维度 | A. GTK3 | B. PySide6 | C. 纯后台 |
|:---|:---:|:---:|:---:|
| 线程模型安全性 | 🔴 差 | 🟢 好 | 🟢 无此问题 |
| 依赖体积 | 🟢 小 | 🟡 大 | 🟢 最小 |
| 旧坑复现风险 | 🔴 高 | 🟢 低 | — |
| 打包复杂度 | 🔴 高（gi 系统依赖） | 🟡 中 | 🟢 低 |
| 可维护性 | 🟡 | 🟢 | 🟡 |

**推荐结论：B. PySide6**。旧项目最密集的事故区就是 GTK 托盘线程；Qt 信号槽天然跨线程安全，可从架构上消除该类 bug。依赖体积大的代价由 onedir 打包（选型五）消化，不影响启动速度。保留「无托盘降级模式」（大纲 §8）作为兜底：`QSystemTrayIcon.isSystemTrayAvailable()` 探测不可用时降级为纯后台 + 通知。

**与旧方案关系**：逻辑参考旧托盘的状态展示/菜单结构/优雅降级思路，实现栈更换。

## 3. 选型二：全局热键方案

> 背景：旧客户端用 pynput 监听 `Ctrl + 反引号`，按住说话、松开停止，X11 下可用。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. pynput（沿用） | 纯 Python、零配置；X11 下稳定；旧项目已验证交互模型 | 🔴 Wayland 下全局监听不可用（XWayland 窗口外失效）；依赖 X 记录扩展 |
| B. evdev（直接读 `/dev/input`） | 不依赖 X11，Wayland 下同样有效；最底层、最可靠 | 需要 `input` 用户组或 root 权限，分发体验差；需自行处理多键盘设备 |
| C. XDG Desktop Portal `GlobalShortcuts` | Wayland 官方正解；沙箱友好 | 需桌面环境支持（KDE 6 / GNOME 48+ 才陆续落地）；按住/松开语义因实现而异；当前生态覆盖不全 |

**综合对比**：

| 维度 | A. pynput | B. evdev | C. Portal |
|:---|:---:|:---:|:---:|
| X11 可用性 | 🟢 | 🟢 | 🟡 |
| Wayland 可用性 | 🔴 | 🟢（需权限） | 🟢（需新桌面） |
| 权限要求 | 🟢 无 | 🔴 input 组 | 🟢 无 |
| 实现复杂度 | 🟢 低 | 🟡 中 | 🟡 中 |

**推荐结论：A. pynput（v1）+ 预留 B/C 抽象层**。当前目标环境为 X11（C5），pynput 已验证可用；但热键监听必须封装为独立模块（大纲 §5-10 约束），内部留出 `HotkeyBackend` 抽象，Wayland 迁移时替换 evdev 或 Portal 后端即可，业务层零改动。

## 4. 选型三：音频录制库

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. PyAudio（沿用） | 旧项目验证可用；PortAudio 成熟稳定 | API 老旧（回调/C 风格）；每次新建 `PyAudio()` 实例开销大（旧项目即有此问题）；打包需带 PortAudio 动态库 |
| B. sounddevice | 同为 PortAudio 绑定，API 现代（NumPy 原生、阻塞/回调双模式）；实例管理清晰 | 旧项目未用过，需重新验证；同样依赖 PortAudio |
| C. soundcard | 纯 Python、无 PortAudio 依赖 | Linux 下走 PulseAudio 高层 API，低延迟控制弱；社区较小 |

**综合对比**：

| 维度 | A. PyAudio | B. sounddevice | C. soundcard |
|:---|:---:|:---:|:---:|
| API 现代性 | 🟡 | 🟢 | 🟢 |
| 成熟度 | 🟢 | 🟢 | 🟡 |
| 资源管理可控性 | 🔴 旧项目踩坑 | 🟢 | 🟡 |
| 依赖 | 🟡 PortAudio | 🟡 PortAudio | 🟢 少 |

**推荐结论：B. sounddevice**。录制参数与旧版一致（16kHz / 单声道 / 16bit），且录音器实例在应用生命周期内复用（根除旧项目每次录音新建 PyAudio 实例的缺陷）。

## 5. 选型四：文字输出方案

> 背景：旧方案「复制→Ctrl+V→0.5s 后恢复剪贴板」存在竞态（大纲 §8 风险项），靠固定 sleep 违反 C2。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. 剪贴板 + Ctrl+V + 恢复原内容（改进版） | 对任意可输入控件通用；粘贴是用户熟悉的语义；长文本瞬时完成 | 需劫持用户剪贴板；恢复时机是核心难点 |
| B. xdotool type 逐字输入 | 不碰剪贴板 | 逐键模拟，长文本慢；中文依赖输入法栈，行为不稳定；旧项目即以此做降级方案 |
| C. IBus/Fcitx 输入法接口提交 | 文本经输入法栈提交，语义最正确 | 两套输入法框架两套接口，复杂度高；用户可能不用 IBus/Fcitx |
| D. uinput 虚拟键盘 | 不依赖 X11 | 同样需要逐键映射中文，权限要求高 |

**综合对比**：

| 维度 | A. 剪贴板改进 | B. xdotool | C. 输入法 | D. uinput |
|:---|:---:|:---:|:---:|:---:|
| 通用性 | 🟢 | 🟡 | 🟡 | 🟡 |
| 长文本速度 | 🟢 | 🔴 | 🟢 | 🔴 |
| 中文可靠性 | 🟢 | 🔴 | 🟢 | 🔴 |
| 实现复杂度 | 🟡 | 🟢 | 🔴 | 🔴 |
| 副作用 | 🟡 劫持剪贴板 | 🟢 无 | 🟢 无 | 🟡 权限 |

**推荐结论：A（主） + B（降级）**，但恢复机制重新设计，根除旧竞态：

1. 备份剪贴板 → 写入识别文本 → 模拟 Ctrl+V
2. **不再固定 sleep**：监听剪贴板所有权被本进程持有的事件，粘贴动作发出后按「焦点窗口粘贴完成」的保守策略延迟恢复，恢复延迟作为**命名常量 + 可配置项**（默认 500ms，注明依据），并在恢复前校验剪贴板内容仍为本进程写入的文本（避免覆盖用户新复制的内容）
3. 剪贴板工具优先 `wl-clipboard`/`xclip` 探测，不可用时降级 xdotool type 并记 warning（🔴 禁止静默降级——降级必须有日志与通知）

## 6. 选型五：打包方案

> 背景：旧服务端 PyInstaller onefile 3.4GB、启动解压 19 秒（冷启动事故根因之一）；旧客户端 Nuitka；打包脚本两套重复漂移。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. PyInstaller onedir | 启动无解压开销（根除旧事故根因 B）；生态最成熟；隐藏导入处理经验丰富 | 产物是目录不是单文件，分发需再封装 |
| B. PyInstaller onefile | 单文件分发方便 | 🔴 大纲 C4 明确排除（旧事故根因） |
| C. Nuitka --standalone | 编译为 C，启动略快、反编译略难 | 构建慢；对 gi/Qt 等重型依赖的兼容问题多（旧客户端踩坑）；onfile 模式同样有解压开销 |
| D. 系统包（deb/rpm） | 最规范 | 维护成本高，v1 不必要 |

**综合对比**：

| 维度 | A. onedir | B. onefile | C. Nuitka | D. 系统包 |
|:---|:---:|:---:|:---:|:---:|
| 启动速度 | 🟢 | 🔴 | 🟡 | 🟢 |
| 构建稳定性 | 🟢 | 🟡 | 🔴 | 🟡 |
| 分发便利 | 🟡 | 🟢 | 🟡 | 🟢 |
| 大纲合规 | 🟢 | 🔴 违反 C4 | 🟡 | 🟢 |

**推荐结论：A. PyInstaller onedir + 外层封装 AppImage**。三组件统一一套打包脚本体系（模板化，根除旧项目脚本重复漂移问题）；onedir 目录打入 AppImage 获得单文件分发便利，AppImage 挂载为只读 squashfs，无解压等待。模型外置目录（大纲 §8），不随二进制分发体积膨胀。启动耗时纳入验收（大纲阶段 4）。

## 7. 选型六：音频传输格式（协议改进一）

> 背景：旧协议把 base64 音频内嵌 JSON，体积膨胀 33%。实测量级：16kHz/16bit/单声道 ≈ 32KB/s，10 秒录音 ≈ 320KB。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. base64 内嵌 JSON（沿用） | 协议最简单，调试肉眼可读；该量级下性能完全够用 | 33% 体积膨胀；大录音下序列化/反序列化有额外 CPU 开销 |
| B. 复合帧：JSON 头 + 二进制音频体 | 无膨胀；头部仍可读可调试；同一连接单帧完成 | 编解码略复杂（两段式长度前缀） |
| C. 双通道（控制 + 数据分离） | 控制面干净；支持未来流式 | 两个连接，状态管理复杂，v1 过度设计 |

**综合对比**：

| 维度 | A. base64 | B. 复合帧 | C. 双通道 |
|:---|:---:|:---:|:---:|
| 传输效率 | 🟡 | 🟢 | 🟢 |
| 实现复杂度 | 🟢 | 🟢 | 🔴 |
| 可调试性 | 🟢 | 🟢 | 🟡 |
| 流式扩展性 | 🔴 | 🟡 | 🟢 |

**推荐结论：B. 复合帧**。帧结构定为 `[4 字节头长度][JSON 头（含 action、音频格式、音频字节数）][原始 PCM 体]`，沿用 4 字节大端长度前缀 + MessageBuffer 的成熟思路，仅多一段定长体；为后续流式识别预留 `audio_chunk` action 的帧复用能力。

## 8. 选型七：配置管理方案

> 背景：旧服务端三套配置源互相矛盾，旧客户端三套并存且 `socket_config.json` 无人读取（大纲 §5-9）。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. pydantic-settings（YAML/JSON 文件 + 环境变量） | 类型校验 + 默认值 + 环境变量覆盖一体；旧服务端已用过（部分经验可继承）；单一入口天然满足 C6 | 引入 pydantic 依赖（服务端本来要装，客户端是新增） |
| B. 手写 JSON + dataclass | 零依赖、直白 | 校验/默认值/环境变量全手写，旧客户端即此方案的实际形态（混乱来源之一） |
| C. TOML + tomllib | 标准库可读；格式适合人写 | 校验仍需自行实现；嵌套表达弱 |

**推荐结论：A. pydantic-settings**。每组件恰好一个 `Settings` 类 + 一个配置文件 + 环境变量覆盖；Socket 路径等全局关键项的**唯一出处**写入协议契约库的默认值，各组件配置仅允许覆盖不允许另立源头。

## 9. 选型八：协议契约库接入方式

> 背景：大纲 §3.2 已定 `Zen_VocoType_Protocol/` 为独立第四组件，本选型定接入方式。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. editable install（`pip install -e ./Zen_VocoType_Protocol`） | 单一出处、改即生效；打包时正常收编进产物；不违反组件独立约束 | 新环境需执行一次安装（写入环境搭建文档即可） |
| B. 各端 vendored 复制 | 零安装步骤 | 🔴 双份定义漂移（旧 GridChat 同款问题），明确排除 |
| C. git submodule + 相对 import | 版本锁定精确 | 违反「文件夹间禁止相对路径 import」；submodule 操作复杂 |

**推荐结论：A. editable install**，与大纲一致。补充约束：契约库版本号内嵌于包，`health` 响应返回协议版本，两端版本不一致时客户端明确报错（🔴 禁止静默继续）。

## 10. 推荐结论汇总

| # | 选型项 | 结论 | 关键理由 |
|:---:|:---|:---|:---|
| 1 | 客户端 UI / 托盘 | **PySide6**（无托盘降级兜底） | 根除 GTK 线程事故区 |
| 2 | 全局热键 | **pynput**（`HotkeyBackend` 抽象预留 evdev/Portal） | X11 已验证；Wayland 留迁移路径 |
| 3 | 录音 | **sounddevice** | 现代 API；实例复用 |
| 4 | 文字输出 | **剪贴板+Ctrl+V 改进版**（xdotool 降级） | 通用性最佳；恢复机制去 sleep 化 |
| 5 | 打包 | **PyInstaller onedir + AppImage** | 根除 onefile 解压事故；统一脚本体系 |
| 6 | 音频传输 | **复合帧（JSON 头 + 二进制体）** | 无膨胀；保留可读头 |
| 7 | 配置 | **pydantic-settings**（每组件单入口） | 满足 C6；类型校验 |
| 8 | 契约库接入 | **editable install + 版本握手** | 单一出处；违反独立性的替代方案均排除 |
