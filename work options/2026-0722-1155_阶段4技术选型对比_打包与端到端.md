## 2. 选型一：PyInstaller onedir 构建体系

> 背景：C2 要求三组件统一模板化脚本。PyInstaller 有两种驱动方式，且需处理 Qt 插件、协议库内嵌、资产 datas 三类共性问题。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. 每组件一个 `.spec` 文件 + 共享构建脚本（模板化参数注入） | spec 是声明式 Python，版本可控、可评审；三组件 spec 结构同构（共用 datas/hiddenimports 模板段），差异仅入口/名称/资产；构建脚本统一调用 `pyinstaller xxx.spec` | spec 文件需维护（模板化后每份仅数十行） |
| B. 命令行参数直调 pyinstaller | 无 spec 文件 | 参数超长不可读；隐式默认值随版本漂移；三组件命令极易各自漂移（旧项目同款问题） |
| C. 第三方封装（pyoxidizer / briefcase） | 构建模型更现代 | pyoxidizer 对 PySide6/torch 重型栈支持不成熟；briefcase 面向 GUI 应用模板，三组件形态不合；🔴 重学成本高收益低 |

**推荐结论：A**。细节：

- 共享模板段：协议契约库自动收编（editable install 的包 PyInstaller 正常识别，无需特殊处理）；资产 `assets/` 经 `datas` 收编；各组件 `config.yaml` 默认配置随包（运行时用户配置仍走配置目录，🔴 禁止把包内配置当唯一源）
- Service 的 torch/FunASR 依赖：onedir 下按 PyInstaller 成熟 hook 收编；构建后执行**体积与启动冒烟检查**（产物存在、二进制可执行、`--version` 类探针可跑）再进入封装
- 构建脚本集中放 `tools/`（项目已有该目录约定），三组件共用入口 `build.py --component service|client|launcher`，产物输出至项目内 `dist/`（C8）；🔴 禁止各组件目录内再长私有打包脚本
- spec 中排除项显式列出（如 Service 排除 Qt、Client 排除 torch），控制产物体积

## 3. 选型二：AppImage 封装工具

> 背景：onedir 目录需封装为单文件。阶段 0 已定 AppImage 路线，工具未定。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. appimagetool + 手写 AppDir（AppRun/.desktop/图标按规范摆放） | 结构完全透明，无魔法；AppRun 只是 exec 入口脚本，三组件同构；构建脚本体系自然延伸（onedir 目录拷入 AppDir → appimagetool 打包） | .desktop/图标规范细节需自己写对（一次到位后模板化复用） |
| B. linuxdeploy + 插件 | 自动处理依赖库收编、桌面文件检查 | 其依赖收编逻辑与 PyInstaller 自收编重叠且可能冲突（双重收编 glibc 等引发玄学问题）；🔴 引入第二层不可控行为 |
| C. appimage-builder | 配方声明式 | 同样自带依赖解析收编，与 PyInstaller 产物定位冲突；生态活跃度一般 |
| D. 不做 AppImage，tar.gz 分发 onedir | 零封装成本 | 双击体验差；桌面入口/图标集成需用户手工；不满足「双击一次拉起全套」验收语义 |

**推荐结论：A**。PyInstaller 已自收编 Python 依赖，AppImage 仅需纯封装不做二次收编——这正是手写 AppDir 最匹配的场景。AppRun 内容：定位自身目录并 exec onedir 内入口二进制（`_APPDIR` 环境变量，🔴 禁止 cwd 相对）；AppDir 内 `.desktop` 与 hicolor 图标按 AppImage 规范摆放（供 AppImageLauncher 类工具集成，见选型五）；运行时环境变量（如 Qt 插件路径）由 PyInstaller 引导逻辑处理，AppRun 不做额外 hack。zsync 更新信息本阶段不做（v2 评估）。

## 4. 选型三：分发形态

> 背景：C6 要求三组件独立交付；但产品使用形态是 Launcher 拉起两端，需定稿产物组织方式。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. 三个独立 AppImage + 约定邻接目录布局 | 每组件独立打包/交付/版本演进（满足 C6）；Launcher 按「自身同目录」自定位查找两端（满足 C8 精神）；用户可只更新其一 | 分发物是三份文件，需提供下载页/说明 |
| B. 单一大 AppImage 内嵌三组件 | 单文件最省心；Launcher 找两端路径最短 | 🔴 三组件捆死，违背「独立打包、独立交付」；任一组件更新需重发全量（Service 含 torch 体积大，更新成本极高） |
| C. 系统包（deb/rpm/AUR） | 最规范的 Linux 分发 | 阶段 0 已排除（维护成本 v1 不必要）；多发行版覆盖工作量大 |

**推荐结论：A**。布局约定：

```
Zen_VocoType/                          # 用户解压/摆放的目录（位置任意）
├── Zen_VocoType_Launcher.AppImage     # 双击入口
├── Zen_VocoType_Service.AppImage
└── Zen_VocoType_Client.AppImage
```

Launcher 的二进制查找顺序：同目录 AppImage → 同目录 onedir 目录 → 配置显式路径，全部缺失时报错提示（阶段 3 选型九差异表的正式模式命令解析）；查找逻辑与 dev 模式的源码拉起共用同一「目标解析」模块。同时保留三组件 onedir 裸产物作为高级用户/调试用途的二级分发物。

## 5. 选型四：模型分发方式

> 背景：C5 —— 旧事故根因之一是「模型路径按 cwd 解析导致随包模型从未生效」。模型体积大（百 MB~GB 级），分发策略影响产物体积与首启体验。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. 模型外置用户目录 + 首次运行按需下载（modelscope 缓存机制） | 产物体积与模型解耦；模型更新不依赖发版；多组件/多版本共享同一份缓存 | 首次使用需联网下载；离线环境需手工放置模型 |
| B. 模型随 Service 产物内嵌 | 开箱即用、离线可用 | 🔴 产物体积爆炸（旧 onefile 3.4GB 教训）；每次发版重传模型；违反 C5「不随二进制分发体积膨胀」 |
| C. 外置 + 独立模型包（可选下载的模型压缩包） | 兼顾离线场景 | 多一条分发线与校验逻辑，v1 范围膨胀 |

**推荐结论：A 为唯一正式路径，C 的「手工放置」作为文档化的离线补救**。细节：

- 模型根目录默认值唯一出处为契约库/Service 配置（用户私有数据目录，遵循 XDG），🔴 禁止程序目录内、禁止 cwd 相对
- 打包后首启验收用例必须覆盖：模型目录为空 → `model_download`/首次切换触发下载 → `ready` 就绪全流程；以及模型已就位 → 直接加载两条路径
- 离线补救：README 文档化「手工下载模型放入指定目录」步骤（含目录结构与校验方式），不提供单独模型包
- AppImage 为只读挂载，模型🔴 严禁写入挂载点内——该约束经「路径自定位 helper」与配置默认值在架构上保证

## 6. 选型五：.desktop 桌面入口与图标集成

> 背景：C7 + 大纲 §3.5 资产迁移约束。桌面入口需在不同集成深度下都能工作。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. 提供模板 .desktop + 安装脚本（写入 `~/.local/share/applications/`，图标进 hicolor 主题目录） | 标准 freedesktop 集成，应用菜单可见、图标正确；不依赖第三方工具 | 需写一个幂等安装脚本（路径模板替换 + `update-desktop-database` 容错） |
| B. 依赖 AppImageLauncher 类守护工具自动集成 | 用户侧零脚本 | 🔴 目标环境未必安装该工具，不可控 |
| C. 只给裸 .desktop 文件让用户自己放 | 零实现 | 体验差；路径写死即坏（旧 `grid_chat.desktop` 即脱节案例） |

**推荐结论：A 为主，B 兼容**。细节：

- `.desktop` 模板中 `Exec=`/`Icon=` 由安装脚本按实际摆放路径渲染（🔴 禁止仓库内写死绝对路径——旧 Launcher 硬编码教训）
- 图标安装到 `~/.local/share/icons/hicolor/<size>/apps/zen-vocotype.png`（多尺寸来自迁移资产 `zen_vocotype_launcher_icon_{32,64,128,256}.png`），图标名与三组件托盘内用图统一命名族
- 安装脚本幂等（重复执行结果一致）、纯用户态（🔴 无需 root）、卸载脚本一并提供
- AppImage 内同时内嵌 .desktop 与图标（选型二），装了 AppImageLauncher 的环境自动集成亦可用

## 7. 选型六：资产随包与运行时加载验证

> 背景：C4 —— 旧 Launcher 图标相对 cwd 在 AppImage 中静默失效（降级为 None 不报错）。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. PyInstaller `datas` 收编 + 统一「程序自身目录」helper（兼容 `_MEIPASS`）+ 缺失记 warning | 各阶段已实现该 helper（阶段 2 托盘图标双环境实测通过），直接复用；行为开发与打包一致 | 需在打包验收中强制双环境截图/自检 |
| B. 图标编译进 Qt 资源系统（qrc） | 单文件内嵌，无路径问题 | 仅覆盖 Qt 客户端；Service/Launcher 非 Qt 或通知图标仍需文件；🔴 两套资产机制并存 |
| C. 运行时从网络/主题获取 | — | 不可控，直接排除 |

**推荐结论：A**。验收强化项：打包环境下三处用图（客户端托盘、Launcher 通知、.desktop 菜单图标）逐一截图留证；图标缺失路径人为注入一次故障测试，确认 warning 日志与降级行为符合预期（🔴 禁止静默 None）。

## 8. 选型七：冷启动耗时测量方法

> 背景：C1 要求「总启动耗时较旧版 66 秒显著下降并有实测数据」；阶段 3 的超时预算也要求 P99 实测回填。测量口径必须先定义。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. 协议级时间戳埋点：Launcher 记录拉起时刻 → `ready` 就绪确认时刻，客户端输出首字时刻另计 | 测量的是用户真实感知的就绪/出字时间；与就绪等待共用同一协议路径，无额外探针；数据自动进验收报告 | 需在 Launcher 日志中结构化输出耗时字段 |
| B. `time` 命令包进程启动 | 零实现 | 只测到进程 fork，不含模型就绪，无意义 |
| C. systemd-analyze / strace 级剖析 | 精细 | 面向系统服务；与本产品形态不合，过度工程 |

**推荐结论：A**。口径定义（写入验收报告模板）：

| 指标 | 定义 | 预算 |
|:---|:---|:---|
| T1 Socket 可连 | Launcher 拉起 Service → 首次建连成功 | ≤ 5s（onedir 无解压，应远优于预算） |
| T2 模型就绪 | 拉起 → `ready` 返回就绪（模型已缓存场景） | 实测回填，目标 ≤ 旧版 66s 的一半 |
| T3 端到端首字 | 双击入口 → 首次按住说话出字（含客户端启动） | 实测回填 |
| T2-cold 冷机模型就绪 | 模型文件已就位但页缓存冷（`echo 3 > drop_caches` 后） | 实测记录，不设硬预算 |

每指标测 N≥5 次取 P99/中位数；原始数据存 `.temp/阶段4验收/`（C8），结论写验收报告。🔴 禁止只报单次最好成绩。

## 9. 选型八：端到端验收自动化方案

> 背景：阶段 4 验收标准要求「打包后冷启动全流程一次成功」+ 图标实测可见。全自动与人工的边界需定稿。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. 分层验收：协议级自动 E2E（打包产物双端互连识别）+ 脚本化场景测试（慢启动/崩溃/幂等）+ 人工确认清单（热键/托盘图标/桌面入口） | 可自动化的全部进 CI 式脚本；真正需要人眼的（真实热键按住、截图确认图标）收敛为短清单，逐项打勾留证 | 人工环节存在，但范围最小化 |
| B. 全自动化（注入输入事件模拟热键 + 截图比对） | 无人工 | X11 注入与真实全局热键路径不完全等价；截图像素比对脆；🔴 投入产出比差 |
| C. 全人工 | 零工具开发 | 不可重复、无回归能力，违反「每阶段验收记录」精神 |

**推荐结论：A**。层次划分：

1. **协议级自动 E2E**：以打包产物（AppImage/onedir）拉起 Service + Client 无头逻辑层，复合帧 `recognize` 真实音频样例识别比对（复用阶段 2 的 E2E 资产与示例语音）
2. **场景脚本**：Launcher 幂等二次执行、模拟慢启动、模拟 Service 崩溃回收（复用阶段 3 单测的 fake 机制，打包版跑冒烟子集）
3. **人工确认清单**：真实按住热键出字、托盘 6 状态色抽查、通知图标、应用菜单图标与双击启动、模型下载首启流程——清单进验收报告逐项 🟢/🔴 留证（沿用阶段 2「真实热键人工验证」同款做法）

## 10. 推荐结论汇总

| # | 选型项 | 结论 | 关键理由 |
|:---:|:---|:---|:---|
| 1 | onedir 构建 | **每组件 spec + `tools/build.py` 统一入口** | 满足 C2；声明式可评审 |
| 2 | AppImage 封装 | **appimagetool + 手写 AppDir（不做二次收编）** | 与 PyInstaller 职责清晰无冲突 |
| 3 | 分发形态 | **三独立 AppImage + 邻接目录约定** | 满足 C6；更新解耦 |
| 4 | 模型分发 | **外置用户目录 + 首启下载（离线手工放置文档化）** | 满足 C5；根除体积膨胀 |
| 5 | 桌面入口 | **模板 .desktop + 幂等安装脚本（hicolor 图标）** | 标准集成；无硬编码路径 |
| 6 | 资产随包 | **datas 收编 + `_MEIPASS` helper + 故障注入验证** | 满足 C4；复用已验证 helper |
| 7 | 耗时测量 | **协议级时间戳 T1/T2/T3，N≥5 取 P99** | 口径即用户真实感知 |
| 8 | E2E 验收 | **协议级自动 + 场景脚本 + 人工短清单** | 可回归；人眼环节最小化 |
