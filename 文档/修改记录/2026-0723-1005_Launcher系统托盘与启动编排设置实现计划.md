# Launcher 系统托盘与启动编排设置实现计划（T40）

## 1. 背景与现状

### 1.1 两个真实痛点

**痛点一：找不到另外两个组件即「静默失败」。**
正式模式下 Launcher 按邻接目录约定解析 Service/Client 二进制
（`targets.py:_resolve_prod_binary`）：以 Launcher 自身所在目录为基准，查找
`Zen_VocoType_Service.AppImage` / `zen_vocotype_service/zen_vocotype_service`
（Client 同理）。用户只要移动了 AppImage、只拷贝了其中一个文件、或三组件
不在同一目录，解析即失败——此时 Launcher 是**纯 CLI 一次性进程**，错误只
体现在退出码 5 + 日志 + 一条 notify-send 通知，用户无图形入口可以补救。

**痛点二：启动编排参数零可调。**
当前编排**硬编码**在 `orchestrator.py`：拉起 Service → 两阶段就绪等待
（Socket 可连 + 模型 ready，最长 180s）→ 拉起 Client → 退出。用户无法：

- 设置「Launcher 启动后多少秒才启动服务端」；
- 设置「服务端启动后隔多少秒再启动客户端」；
- 调整两个组件的启动位置（二进制路径）。

### 1.2 托盘的定位（用户明示，v2 核心）

托盘**不是常驻守护**，定位是「**设置与观察的窗口**」：

- 托盘图标 + 右键菜单 = 设置入口（双延迟、组件位置）+ 状态观察（两端运行
  状态、编排进度、错误可见——🔴 不要静默出错）；
- **成功路径自行关闭**：编排完成（两端拉起）后 Launcher 自行退出；
  若「拉起后立即关」实现有障碍，兜底方案为**定时关闭**（可配置秒数）；
- **失败路径不自动关闭**：出错时托盘停留，错误态可见、可经菜单补救
  （设置位置/重试），用户手动退出——静默失败比常驻更不可接受。

### 1.3 Launcher 当前形态

选型七方案 A：Launcher 是「拉起确认就绪后即退出」的一次性编排进程，零 GUI
（通知走 notify-send），spec 明确排除 PySide6 与 ML 栈控制体积（现状
AppImage 48M）。托盘化引入 Qt，但**进程生命周期不变**——仍然是「拉起两端
后即退出」，只是退出前多了一个可观察、可设置的托盘窗口期。

### 1.4 关键存量资产（调研结论，本计划大量复用）

| 资产 | 位置 | 本计划用途 |
|---|---|---|
| 邻接目录解析 + 显式路径配置 | `targets.py`（`service_binary`/`client_binary` 字段已存在于 `config.py`） | 「启动位置」设置的**落点字段已存在**，本计划只是给它加图形入口与持久化，解析逻辑零改动 |
| 用户配置文件层 | 契约库 `zen_vocotype_protocol.user_config`（`set_user_config_value`） | **持久化的唯一合法落点**：写入 `$XDG_CONFIG_HOME/zen_vocotype/user_config.yaml`，重启经配置源链自动生效；🔴 禁止写包内 config.yaml（AppImage 只读） |
| 托盘实现范式 | Service `tray/tray.py`（PySide6 QSystemTrayIcon + QMenu + Signal 外抛、「托盘零业务逻辑」边界、action 持久持有防 GC） | Launcher 托盘直接镜像该范式；GC 陷阱教训已沉淀 |
| 图标加载 | Launcher `icon_loader.py`（双环境解析、四档图标、缺失降级不崩溃） | 现为通知图标服务，托盘图标**原样复用**（返回路径包一层 QIcon 即可） |

## 2. 目标与非目标

### 2.1 目标

1. Launcher 默认以**托盘形态**运行：系统托盘图标可见、右键菜单可用；
   保留 `--no-tray` 一次性 CLI 模式（兼容既有用法与冒烟探针），无显示环境
   （无 `$DISPLAY`/Wayland）自动回退 `--no-tray` 并记日志。
2. 托盘菜单实时展示两端状态与编排进度（未启动/等待中/运行中/失败），
   🔴 全程不要静默出错——错误必须出现在菜单状态行与通知里。
3. 启动顺序**固定：先服务端，后客户端**（不提供反向）。
4. 菜单图形化设置以下参数，**即时生效（对下一次编排）+ 持久化**：
   - **服务端启动延迟**（`service_start_delay_s`）：Launcher 启动后多少秒
     才拉起服务端（秒，默认 0）；
   - **客户端启动间隔**（`client_start_interval_s`）：服务端拉起后隔多少
     秒再拉起客户端（秒，默认 0，语义见 §3.3）；
   - **组件位置**：Service / Client 二进制路径（文件选择对话框，写回既有
     `service_binary`/`client_binary` 字段）。
5. **成功后自行关闭**：编排成功（两端拉起并就绪）后托盘短暂展示完成态，
   经可配置延迟自动退出（`auto_exit_delay_s`，默认 5 秒，0 = 立即）；
   失败路径托盘停留不自动退出（§1.2）。
6. 目标解析失败（找不到组件）时：状态行明确错误 + 「设置位置…」入口
   直达补救，🔴 禁止只剩退出码与日志。
7. 打包链路同步：launcher spec 移除 PySide6 排除并收编，构建冒烟照旧通过。

### 2.2 非目标

- 不改 Service / Client / 协议库任何代码
- 不提供「先客户端后服务端」顺序（用户明示固定先服务端）
- 不做托盘内「停止/重启两端」（Launcher 选型七红线：无权终止非本进程拉起
  的实例）
- 不做通用设置中心对话框（设置项走菜单，与 Client 托盘同风格）
- 不改变 `--dev` 模式行为（dev 模式维持一次性 CLI，托盘设置项对其不生效
  并在菜单置灰说明）

## 3. 方案设计

### 3.1 进程生命周期（v2 核心：托盘化但「拉起两端后即退出」）

```
main.py
  ├─ --version          → 探针原样（配置/日志初始化前返回，零写盘）🔴 不动
  ├─ --dev / --no-tray  → 现状一次性 CLI 路径（orchestrator.run 后退出）🔴 不动
  └─ 默认（有显示环境）  → 托盘模式：
       ① QApplication 创建（须真实显示；创建失败回退 CLI 并记日志）
       ② 抢 Launcher 锁（已被持有 → 通知「已在运行」退出码 2）
       ③ LauncherTray 显示（图标 = icon_loader 四档）
       ④ QThread 工作线程执行 orchestrator.run（deps 注入状态回调桥接 Qt Signal）
       ⑤ 编排期间托盘可观察、可设置（设置作用于下一次编排，不打断进行中）
       ⑥ 成功 → 状态行「已完成」→ QTimer 倒计时 auto_exit_delay_s →
          释放锁 → 自行退出（退出码 0）
       ⑦ 失败 → 托盘停留：状态行红字错误 + 通知 + 补救入口（设置位置/重试/
          手动退出）——🔴 不自动退出（防静默失败）
```

- **「拉起后自行关闭」可行性**：完全可行（进程是我们自己的，编排函数返回后
  `QApplication.quit` 即可），无需退化到「定时关闭」兜底；
  `auto_exit_delay_s` 是观察窗口而非实现障碍的妥协——用户想「拉起来就关」
  设为 0 即可。
- **编排线程化**：`orchestrator.run` 阻塞（就绪等待最长 180s+），🔴 禁止跑
  在 Qt 主线程（托盘冻结）。QThread 执行，状态变更只经 Qt Signal 回主线程
  （🔴 禁止工作线程直触 QWidget）。
- **orchestrator 侵入最小化**：`run()` 本体不改签名，`OrchestratorDeps`
  新增可选 `status_callback: Callable[[str], None] | None`（默认 None，CLI
  路径零影响）；双延迟经 `targets.build_plan` 产出的 `LaunchPlan` 携带，
  不进 `run()` 参数列表。

### 3.2 新配置字段（config.py）

| 字段 | 类型/约束 | 默认 | 说明 |
|---|---|---|---|
| `service_start_delay_s` | `float`，`Field(ge=0, le=300)` | `0.0` | Launcher 启动后多少秒才拉起服务端 |
| `client_start_interval_s` | `float`，`Field(ge=0, le=300)` | `0.0` | 服务端拉起后隔多少秒再拉起客户端（§3.3 语义） |
| `auto_exit_delay_s` | `float`，`Field(ge=0, le=60)` | `5.0` | 编排成功后托盘的观察停留秒数，0 = 立即退出；仅托盘模式有效，CLI 模式无视（CLI 本就跑完即退） |

`service_binary` / `client_binary` 字段**已存在**，不新增。

环境变量随 pydantic-settings 前缀自动生成
（`ZEN_VOCOTYPE_LAUNCHER_SERVICE_START_DELAY_S` 等），菜单设置时检测存在即
通知提醒（沿用 T33/T35 模板：ENV_VAR 常量集中声明，🔴 禁止散落硬编码）。

### 3.3 双延迟的编排语义（orchestrator/targets）

- `LaunchPlan` 增字段 `service_delay_s: float`、`client_interval_s: float`
  （dataclass 默认 0.0 保持向后兼容，既有测试零破坏）；`build_plan` 从
  Settings 读入（dev 模式强制 0，托盘菜单两项置灰标注「dev 模式固定」）。
- 编排流程调整为：

```
抢锁 → 识别既有实例（幂等分支不变）
     → sleep(service_delay_s)（>0 时；状态回调「将于 N 秒后启动服务端」）
     → 拉起 Service
     → sleep(client_interval_s)（>0 时；状态回调「N 秒后启动客户端」）
     → 拉起 Client（存活确认不变）
     → 两阶段就绪等待（Socket 可连 + 模型 ready，超时上限不变）
     → 完成/失败
```

- **客户端拉起门控由「就绪确认」改为「固定间隔」**（v2 按用户意图调整）：
  现状是「等模型 ready 才拉客户端」，改为「间隔到达即拉客户端」。依据：
  Client 是懒连接（识别请求时才连 Socket，启动期不依赖 Service 存活，
  §1.4 资产），先拉起无害；就绪等待**保留**，但位置后移为「两端拉起后的
  整体成败判定」，超时仍报错 + 通知（客户端侧由既有「重连一次 + 托盘
  手动重试」兜底）。
- 间隔为 0 时行为：两端背靠背拉起后就绪等待——与现状的差异仅是「客户端
  不再等模型 ready」，启动总耗时反而更短（客户端初始化与模型加载并行）。
- `time.sleep` 经 deps 注入（`OrchestratorDeps.sleep`，默认 `time.sleep`），
  测试替换为 fake，🔴 禁止真实睡眠拖慢测试；睡眠期间 status_callback 按秒
  倒计时回调（托盘状态行显示剩余秒数）。

### 3.4 托盘菜单结构（新子包 `tray/`）

新建 `src/zen_vocotype_launcher/tray/`（`__init__.py` + `tray.py`），镜像
Service 托盘范式（QSystemTrayIcon + QMenu + Signal 外抛 + action 持久持有）：

```
Zen_VocoType Launcher v1.1              （禁用展示行）
Service：○未启动   Client：○未启动       （禁用状态行，编排回调实时刷新）
进度：将于 3 秒后启动服务端…             （禁用进度行，倒计时/阶段文本）
─────────────────────────────────
立即启动                                （触发编排；编排进行中置灰）
重新检测状态
─────────────────────────────────
服务端启动延迟（0 秒）…                  （QInputDialog.getInt，0~300，预填当前值）
客户端启动间隔（0 秒）…                  （同上）
成功后自动退出（5 秒）…                  （QInputDialog.getInt，0~60）
─────────────────────────────────
Service 位置：未设置（自动）…            （QFileDialog 选文件；已设置显示文件名）
  └ 恢复自动解析                        （清除已设路径，回到邻接约定）
Client 位置：未设置（自动）…
  └ 恢复自动解析
─────────────────────────────────
退出启动器（不影响已启动组件）
```

- 状态行三态起步：○未启动 / ◐等待中（倒计时）/ ●运行中；失败显
  「✗ 未找到二进制」等红字错误，「位置…」项成为直达补救入口——
  **痛点一的图形化闭环**；
- 设置沿用「校验 → 先落盘 → 后切内存 → 刷菜单文本 → 通知」编排，失败
  整体不生效（T33/T35 模板）；
- 「退出」文案明示不影响两端（选型七红线），不加二次确认（无害操作）。

### 3.5 打包与依赖同步

## 5. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 客户端拉起门控从「就绪确认」改为「固定间隔」，间隔不足时用户立即识别会报「服务端未就绪」 | Client 懒连接 + 断线重连一次 + 托盘手动重试兜底（§1.4 资产）；README 调参指引说明「模型加载慢的机器间隔给足（如 10~20s）」；就绪等待保留为整体成败判定，超时报错不静默 |
| 双延迟期间用户疑惑「没反应」 | 进度行按秒倒计时（「将于 N 秒后启动服务端」），🔴 不做无声等待 |
| 成功自动退出被误解为「崩溃消失」 | 退出前完成态通知（notify-send 既有通道）+ 状态行「已完成，N 秒后退出」倒计时；失败路径明确不自动退出，对比可感知 |
| 托盘线程与 Qt 主线程竞态（工作线程直触 QWidget 崩溃） | 编排全程 QThread，状态回主线程只经 Signal；offscreen 测试覆盖回调路径 |
| PySide6 顶层 import 拖慢/破坏 `--version` 探针 | 托盘相关 import 全部延迟到托盘分支函数内；探针零写盘回归用例固化 |
| 用户经文件对话框选了不可执行/错误文件 | 设置时校验：存在 + 可执行位 + 是文件，不满足即通知拒绝落盘 |
| Launcher 体积翻倍（48M→约 110M） | 已评估可接受（§3.5）；ML 栈排除保留，体积增量仅 Qt 本体 |
| 用户配置文件被手改为非法值 | pydantic 构造期校验兜底（现状机制），启动即明确报错退出码 5 |
| dev 模式行为漂移 | build_plan dev 分支强制 0 + 菜单置灰 + 单测固化 |

## 6. 待审阅确认点

1. **自动退出延迟默认值**：`auto_exit_delay_s` 默认 5 秒（观察窗口，本计划
   方案）vs 默认 0（拉起来立即关）——本计划取 5s，给你看一眼「已完成」
   的余地；想立即关可设为 0。
2. **延迟上限**：双延迟 UI/字段上限 300s（5 分钟）是否合适。
3. **客户端门控语义**：间隔到达即拉客户端、就绪等待后移为整体判定
   （本计划方案，启动更快）vs 维持「就绪确认后 + 额外间隔」再拉客户端
   （更保守但间隔感受被模型加载时间淹没）——本计划按你的意图取前者。
4. **「恢复自动解析」子项**：位置已设置后提供清除回邻接约定的入口
   （本计划：提供）。
5. **失败后重试**：托盘停留时「立即启动」项直接作为重试入口（本计划
   方案），不另设「重试」项。
