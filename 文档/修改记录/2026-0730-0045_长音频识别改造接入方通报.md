## 1. 结论

需求说明书提出的长音频识别能力已按**方案 B（实现协议预留的 `audio_chunk` 流式通道）**落地，四组件版本 **1.4** 同批发布。单段 **≥2 小时**连续音频可分片上传识别，服务端全程无大规模内存驻留（会话 PCM 落盘 XDG data 目录）。

## 2. 协议版本与部署要求

- 协议版本 **1.4**；`is_compatible` 严格相等语义不变——🔴 **1.3 客户端连接 1.4 服务端将被 1003 拒绝**，请与服务端同批升级，勿混合版本部署
- 官方客户端/Launcher 业务代码零改动（不发 `audio_chunk`），仅版本同步

## 3. `audio_chunk` 接入要点（语义详见协议设计文档 v1.1 §3.6）

1. **三阶段**：`begin`（头级 `audio_format` + `chunk` 对象，可选 `total_bytes` 预告）→ `N×data`（PCM 分片 ≤ 单帧体上限约 10 分钟，`seq` 从 0 严格递增，响应 `received_bytes` 即进度）→ `end`（触发整段识别，响应同 `recognize` payload）
2. **chunk 对象构造/校验以契约库 `zen_vocotype_protocol.chunk` 为单一出处**（`new_session_id` / `build_chunk_begin|data|end`），🔴 请勿自行拼字典
3. **会话规则**：单连接单活跃会话；会话绑定连接（断连即销毁，🔴 不支持跨连接续传）；空闲 120s 销毁；累计上限 256MB ≈ 2.2 小时（超限 4004）
4. **新错误码**：4003（会话状态非法：不存在/乱序/跳号/重复）、4004（会话超上限）
5. **end 帧 I/O 超时须按音频时长自行设定**（≈ 音频时长 × RTF × 安全系数 2；GGUF 引擎 RTF 保守取 0.2，2 小时音频 ≈ 48 分钟），🔴 禁止沿用短音频静态值
6. 模型切换中收到 end → 2002（**会话保留**，稍后重发 end 即可）

## 4. 识别结果新字段（`recognize` 与 `audio_chunk` end 共用，纯追加）

| 字段 | 说明 |
|:---|:---|
| `segments` | 时间戳分段 `[{start_ms, end_ms, text}]`。**⚠️ 默认引擎 funasr-gguf 不产出本字段**（vendor CLI 无时间戳能力，2026-07-30 实测调研）；`funasr` 引擎（sensevoice-small）产出。给不出时字段整体省略，🔴 消费方须按「字段可缺席」解析 |
| `language` | 语种码（如 `zh`），仅 SenseVoice 引擎产出 |

下游管线若依赖时间戳，当前默认引擎下需以 `segments` 缺席为常态设计（或改用 sensevoice-small 引擎）。

## 5. 迁移建议

- 接入方既有的「客户端分块兜底」逻辑**可移除**：长音频直接走 `audio_chunk`，服务端聚合落盘后整段识别
- `recognize` 单帧路径行为与结果结构完全保留（仅 payload 纯追加），存量调用零改动
- qwen3-asr 引擎单段上限 20 分钟，超限返回 4001（message 含 `engine_limit`），不会静默截断
