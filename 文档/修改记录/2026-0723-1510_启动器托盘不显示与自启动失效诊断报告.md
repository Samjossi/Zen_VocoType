# 启动器「托盘不显示」与「自启动未拉起两端」诊断报告

## 0. 结论速览

| 症状 | 根因 | 性质 |
|---|---|---|
| ① 启动器运行后看不到托盘图标（功能正常，两端被拉起/已在运行） | `auto_exit_delay_s` 被持久化为 **0**（实机调试期写入用户配置文件）+ 两端已在运行时编排**幂等命中秒级完成** → 启动器进程 1~2 秒内退出，GNOME 托盘图标注册是异步的，**图标来不及出现在面板上** | **设计行为，非缺陷**（T40：0 = 立即退出） |
| ② 自启动没有拉起两端 | 本项目**没有任何自启动功能**（全仓 grep `autostart/自启动/开机启动` 零命中）；`tools/install_desktop.py` 只安装**应用菜单入口**（`~/.local/share/applications/`），不等同自启动。用户侧的自启动配置未生效，属外部配置问题 | **需求缺口 + 外部配置** |

两个症状均与「打包成 AppImage」无关——用户已实测源码运行
（`uv run python Zen_VocoType_Launcher/main.py`）同样无托盘，排除打包形态因素。

## 1. 证据链（2026-07-23 15:09 三枚探针，零副作用）

### 探针 1：当前生效配置（`Settings()` 实例化实测）

```
auto_exit_delay_s      = 0.0    ← 关键：立即退出（默认应为 5.0）
service_start_delay_s  = 4.0
client_start_interval_s= 8.0
service_binary         = None（自动解析）
client_binary          = None（自动解析）
```

`auto_exit_delay_s=0` 是**用户配置文件**（`~/.config/zen_vocotype/user_config.yaml`）
中的持久化值——对应 T40 实机调试期经托盘菜单写入的设置（见 commit
699d54f 消息中「实机调试写入 4/8/12 秒」的同类记录）。默认 5 秒观察窗口
被改为 0 后，成功路径不再停留。

### 探针 2：显示环境与 Qt 托盘可用性

```
DISPLAY = :1；XDG_CURRENT_DESKTOP = ubuntu:GNOME
QSystemTrayIcon.isSystemTrayAvailable() = True
```

桌面托盘服务**正常可用**——排除「SNI 不可用导致图标不显示」的假设。

### 探针 3：目标解析与两端实时状态

```
service bin → ~/AppImages/zen_vocotype_service.appimage（~/AppImages 兜底命中）
client  bin → ~/AppImages/zen_vocotype_client.appimage
service → RUNNING（pid=14149，幂等命中）
client  → RUNNING（pid=14276，幂等命中）
```

两端**早已在运行**——症状①发生时启动器走的是幂等快速路径。

### 代码侧闭环

- `orchestrator.py:163-164`：**仅在需要拉起时才倒计时**；既有实例幂等命中
  不等待 `service_start_delay_s`——幂等编排 1~2 秒即完成；
- `app.py:328-338` `_start_auto_exit`：`delay <= 0` 且菜单未打开 →
  记日志「编排成功，立即退出（auto_exit_delay_s=0）」→ `QApplication.quit()`；
- GNOME（AppIndicator 扩展）的 StatusNotifierItem 注册经 D-Bus 异步完成，
  面板图标出现本身有百毫秒级延迟——进程在注册完成前退出，图标**从未
  有机会出现**。

### 症状①完整时序

```
launcher 启动 → 托盘 show()（图标注册中…）→ 状态检测：两端 RUNNING
  → 编排幂等命中（跳过 4s/8s 倒计时，~1-2s 完成）
  → 成功 → auto_exit_delay_s=0 → 立即 quit
  → 托盘图标尚未注册到面板，进程已退出 ⇒ 用户视角「没有托盘」
```

「功能正常、两端被拉起」的观察也吻合：用户看到的服务端/客户端托盘与
进程，是**此前已在运行的两端**（或幂等确认），启动器本体一闪即退。

> 旁证：若两端未运行（冷启动场景），编排含 4s 延迟 + 模型就绪等待
> （缓存约 12s）+ 8s 间隔 ≈ 30 秒，托盘图标有充足时间出现——此时即使
> `auto_exit_delay_s=0` 也能看到托盘。本次两端已在运行，踩中的正是
> 「幂等秒退」组合。

## 2. 症状②分析：自启动未拉起两端

### 项目侧事实

1. **本项目无自启动功能**：全仓（三组件 + tools + 文档）grep
   `autostart|自启动|开机启动` 零命中；
2. `tools/install_desktop.py` / `desktop_entry.py` 只写入
   `~/.local/share/applications/zen-vocotype.desktop`（应用菜单入口）+
   hicolor 图标，**不写 `~/.config/autostart/`**——「安装桌面入口」≠
   「开机自启动」；
3. 启动器对自启动场景**本身兼容**：登录会话中 `DISPLAY` 已设置，托盘
   模式可进入；即使 SNI 尚未就绪导致图标不显示，CLI 回退路径
   （`main.py:110-120`）也会完整执行编排——即「自启动配置只要真把
   启动器跑起来，两端就会被拉起」。

### 推论

自启动未拉起两端 ⇒ **启动器在登录时根本没有被执行**（若执行了，无论
托盘/CLI 路径都会拉起两端）。可能的失效点（按可能性排序，需用户侧
确认，这些路径在项目目录之外，本报告不越界读取）：

| # | 候选失效点 | 用户自查命令 |
|---|---|---|
| 1 | 从未真正配置自启动（误以为 install_desktop.py 即自启动） | `ls ~/.config/autostart/` 看有无 zen 相关条目 |
| 2 | 自启动条目 Exec 路径指向已被移动/删除/改名的 AppImage（今天 13:39/14:58 两次重新打包，若条目指向旧副本路径或大小写不符的文件名，如 `Zen_VocoType_Launcher.AppImage` vs `zen_vocotype_launcher.appimage`） | `cat ~/.config/autostart/*.desktop \| grep -i -A2 zen`；`ls -l` 对照 Exec 路径 |
| 3 | 桌面环境自启动机制未启用该条目（GNOME Tweaks 中关闭/条目含 `Hidden=true`） | 同上；GNOME Tweaks「开机启动程序」面板核对 |
| 4 | Exec 命令语法问题（路径含中文目录未加引号等） | 手动在终端原样执行条目中的 Exec 行验证 |

> 注：`~/AppImages/` 下两端二进制为**小写命名**
> （`zen_vocotype_service.appimage`），与 `dist/` 产出的官方命名
> （`Zen_VocoType_Client.AppImage`）不同——若自启动条目按官方命名指向
> `~/AppImages/`，文件不存在即静默失败（桌面环境对失效 Exec 通常无提示）。

## 3. 处置建议（均非必须，按优先级排序）

### 3.1 立即恢复托盘可见（用户操作，零代码）

托盘菜单「成功后自动退出（0 秒）…」改回非 0（如默认 5 秒），或直接编辑
`~/.config/zen_vocotype/user_config.yaml` 删除/修改 `auto_exit_delay_s: 0`。
改回后即使幂等秒完，托盘也会停留观察窗口，图标可见。

### 3.2 UX 改进候选（如需立项，另出计划）

- **P2：`auto_exit_delay_s=0` 时发桌面通知**「启动完成」——保留立即退出
  语义但消除「无声无息」的视觉真空（`notify.py` 通道现成）；
- **P3：托盘模式启动即发「编排开始」通知**——覆盖 GNOME SNI 注册延迟
  场景，进程多短用户都有反馈；
- **P3：README「成功后自动退出」节补充说明**：0 = 立即退出且可能看不到
  托盘图标（尤其在两端已运行的幂等场景）。

### 3.3 自启动支持（需求缺口，如需立项）

- `tools/desktop_entry.py` 增加 `--autostart` 选项：同模板渲染
  `~/.config/autostart/zen-vocotype.desktop`（加
  `X-GNOME-Autostart-enabled=true`），幂等、卸载对称；
- 或在 Launcher 托盘菜单加「开机自启动」勾选项（写 autostart 条目，
  与三延迟设置项同范式）。
