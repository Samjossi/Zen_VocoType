# fun-asr-nano 速度问题实测报告

## 一、问题缘起

2026-07-23 默认引擎迁移 `fun-asr-nano` 后，用户实测反馈：**识别完成后文本
上屏明显迟滞，手感慢于已移除的 paraformer-large**，并推测「不是模型问题而是
流程问题」。本报告记录完整排查过程与实测结论。

## 二、排查一：流程延迟审计（结论：流程无延迟）

对「识别完成 → 文本上屏」全链路逐段代码审计：

| 环节 | 机制 | 延迟量级 |
|---|---|---|
| 服务端推理 → 响应 | worker 单线程独占，推理完直接返回 | ~0 |
| Socket 传输 | Unix 域阻塞式 recv，无轮询无 sleep | 毫秒级 |
| 客户端信号 → 主线程 | Qt 队列信号 | 毫秒级 |
| 剪贴板写入 + 模拟 Ctrl+V | 识别文本到达**立即执行** | 毫秒级 |
| 剪贴板恢复延迟 `paste_restore_delay_ms` | 发生在**粘贴之后**，仅影响原剪贴板恢复时机 | 对上屏=0 |

**结论**：链路上唯一的延迟设计（剪贴板恢复）在粘贴之后发生，不可能拖延
上屏。流程假设被否证。

## 三、排查二：双引擎同音频对拍（结论：模型本身差 10 倍）

同机（AMD Ryzen 9 9955HX）、同音频、同调用路径（`run_inference`），稳态：

| 音频时长 | paraformer-large | fun-asr-nano（PyTorch） |
|---|---|---|
| 3s | 0.1s（RTF 0.03） | 1.0s（RTF 0.34） |
| 10s | 0.3s | 2.9s |
| 30s | 0.8s | 8.7s |
| 165.7s（拼接长音频） | ~5s（RTF 0.03） | 45.2s（RTF 0.273） |

折算日常手感：5 秒语音 paraformer ≈0.15s 上屏，fun-asr-nano ≈1.5s；
15 秒则 0.45s vs 4.4s。**用户感受到的迟滞即此差距，与流程无关。**

补测排除项：`language="中文"` 参数（跳过语种识别的理论提速点）实测
2.9s → 2.9s **无收益**——nano 的慢是自回归逐 token 解码的固有成本。

### 参照系修正（教训）

此前 description 称 fun-asr-nano「RTF≈0.34 日常可用」，参照系是实时率 1.0
（比说话快即可用）。但**语音输入法的真正基准是 paraformer 的 RTF 0.03**——
「比实时快 3 倍」与「说完即贴」是两个量级的手感。评估选型时须以
**同场景既有引擎**为基准，而非绝对实时率。

## 四、排查三：核显加速可行性（结论：不可行）

本机硬件事实：

| 项 | 事实 |
|---|---|
| CPU | AMD Ryzen 9 9955HX（Zen 5，16 核 32 线程，最高 5.46GHz） |
| 核显 | Radeon 610M（PCI 1002:13C0，RDNA2，**仅 2 个计算单元**，亮机级） |
| ROCm | 未安装；且官方不支持 gfx1035 iGPU（需 `HSA_OVERRIDE_GFX_VERSION` 黑科技，脆弱） |
| Vulkan | RADV 驱动在（`radeon_icd.json`），但 2CU 算力 <1 TFLOPS，对 0.8B 模型收益可能为负 |

**结论**：核显路线不值得投入。16 核 Zen 5 CPU 本身算力充沛，提速应在
软件栈（推理运行时）上找。

## 五、排查四：GGUF/llama.cpp 运行时实测（结论：快 2~4.4 倍，精度无损）

FunASR 官方 2026-06 发布 Fun-ASR-Nano 的 GGUF 量化版与 llama.cpp 原生
C++ 运行时（whisper.cpp 同款，单二进制零 Python）。本机实测环境：

- 运行时：官方预编译 `funasr-llamacpp-linux-x64-avx2`（v0.1.4）
- 权重：`funasr-encoder-f16.gguf`（470MB）+ `qwen3-0.6b-q4km.gguf`（484MB）
  + `fsmn-vad.gguf`（内置 VAD）

实测结果（同音频、同机）：

| 音频 | PyTorch 路径 | **GGUF q4km 路径** | 加速比 |
|---|---|---|---|
| 2.8s 短语音 | 0.9s | **0.57s**（含进程启动+mmap 模型加载，全程 wall 0.614s） | ~1.6× |
| 165.7s 长音频 | 45.2s | **10.2s（RTF 0.062，54 个 VAD 分段）** | **4.4×** |

关键观察：

1. **mmap 使进程级调用开销极小**：GGUF 按需分页 + OS 页缓存，CLI 单次
   调用（含「加载」470MB+484MB 权重）总开销仅 ~0.1s——以子进程方式集成
   进服务端完全可行，无需常驻进程。
2. **精度**：官方 184 段基准 q4km CER 8.35% vs q8_0 8.30%（差距 <0.1%）；
   本机测试样本识别文本与 PyTorch 版逐字一致。
3. **手感折算**：5 秒语音上屏等待从 ~1.5s（PyTorch）降至 ~0.7s（GGUF），
   接近 paraformer 的「说完即贴」（RTF 0.03）体验。
4. GGUF 官方速度数据（q4km 6.1× 实时 ≈ RTF 0.164）与本机长音频实测
   RTF 0.062 同量级甚至更好（16 核 Zen 5 强于官方测试机）。

## 六、结论汇总

| 问题 | 结论 |
|---|---|
| 慢在流程还是模型？ | **模型**。流程全链路毫秒级，无可优化空间 |
| 慢多少？ | PyTorch 路径 fun-asr-nano 比 paraformer 慢约 **10 倍**（RTF 0.03 vs 0.29-0.34） |
| 核显能救吗？ | **不能**。Radeon 610M 为 2CU 亮机核显，ROCm/Vulkan 路线均不成立 |
| 有效解法？ | **官方 GGUF/llama.cpp CPU 运行时**：实测快 2~4.4 倍（RTF 0.062），精度 <0.1% CER 损失，可子进程形态集成 |
| 新词问题怎么办？ | 保留 fun-asr-nano 正确（2025-12 训练数据）；其热词注入能力可后续进一步增强 |
