## 1. 传输层

| 项 | 定稿 |
|:---|:---|
| 传输 | Unix Domain Socket（`SOCK_STREAM`） |
| 路径默认值 | 生产/开发均为**用户私有运行目录**下（`$XDG_RUNTIME_DIR`，回退 `~/.local/run`）：`zen_vocotype.sock` / `zen_vocotype_dev.sock`（契约库 `paths.py` 唯一出处，组件配置仅可覆盖；🔴 禁止默认使用全局可写 /tmp——可预测路径在多用户系统可被抢先 bind 冒充服务端） |
| 连接模型 | Client 长连接复用；Launcher 按需短连接（`ready` 轮询）；长音频接入方（如 AI_Video_Transcriber）独立长连接 |
| 并发 | 单用户本机场景；服务端按连接逐一处理，同连接内请求—响应严格有序 |

## 2. 帧格式（复合帧）

```
┌────────────────────┬──────────────────────┬─────────────────────┐
│ 4 字节大端头长度 N  │ JSON 头（UTF-8，N 字节）│ 二进制体（可为空）    │
└────────────────────┴──────────────────────┴─────────────────────┘
```

- **头长度 N**：仅统计 JSON 头字节数，不含自身 4 字节、不含二进制体
- **二进制体**：长度由 JSON 头中的 `audio_bytes` 字段声明（无体时省略该字段或置 0）
- **防御性上限**：请求方向头 ≤ 64KB；体 ≤ 约 10 分钟 PCM（`frames.py` 中 `MAX_HEADER_BYTES` / `MAX_BODY_BYTES`），超限即判帧损坏，服务端记录错误并关闭连接。🔴 本上限在 v1.4 **不动**——它是对语音输入场景的单帧防御语义；长音频经 §3.6 `audio_chunk` 分片承载，每片仍受本上限约束
- **响应方向头上限放宽（v1.4）**：识别文本在响应头 payload 内，长音频文本体积可观（2 小时中文识别 ≈ 4 万字 ≈ 123KB，超 64KB）；响应方向头 ≤ 4MB（`frames.py` 中 `MAX_RESPONSE_HEADER_BYTES`，防失控兜底而非防恶意——响应为服务端自产）。服务端编码响应、客户端解析响应用本值；服务端解析请求、客户端编码请求仍用 64KB
- **粘包处理**：沿用旧项目验证可用的 MessageBuffer 思路（持续 feed 字节流、逐帧取出），重新实现不复制

与旧协议差异：旧协议把 base64 音频内嵌 JSON（33% 体积膨胀）；复合帧头保持 JSON 可读可调试，音频走原始 PCM 体，零膨胀。

### 2.1 JSON 头字段

| 字段 | 类型 | 方向 | 必填 | 说明 |
|:---|:---|:---|:---:|:---|
| `action` | string | 双向 | ✅ | 见 §3 action 全集 |
| `protocol_version` | string | 双向 | ✅ | 协议版本号（§5 版本握手） |
| `request_id` | string | 请求方生成，响应方回显 | ✅ | 请求—响应配对；UUID 即可 |
| `ok` | bool | 响应 | ✅ | `true` 成功 / `false` 失败 |
| `error` | object | 响应 | 失败时必填 | `{"code": int, "message": str}`，错误码见 §4 |
| `audio_format` | object | 请求（含音频时） | 含音频时必填 | `{"sample_rate": 16000, "channels": 1, "sample_width": 2}` |
| `audio_bytes` | int | 请求（含音频时） | 含音频时必填 | 二进制体字节数，服务端据此校验实际收到长度 |
| `chunk` | object | 请求（`audio_chunk`） | 该 action 必填 | 流式会话阶段对象（§3.6，契约库 `chunk.py` 单一出处） |
| `payload` | object | 双向 | 视 action | 各 action 业务字段容器（§3） |

### 2.2 响应总约定

- 成功：`"ok": true` + `payload` 携带结果
- 失败：`"ok": false` + `error.code` / `error.message`；🔴 任何失败必须显式返回错误响应，禁止超时静默、禁止占位结果（旧假模型兜底为反面案例）
- `request_id` 必须回显请求方的值

## 3. Action 全集

> 常量定义见契约库 `actions.py`；`ALL_ACTIONS` 用于服务端入站校验，未知 action 返回 `1002`。

### 3.1 `health` — 健康检查

- **方向**：Client/Launcher → Service
- **请求 payload**：无
- **成功响应 payload**：

| 字段 | 类型 | 说明 |
|:---|:---|:---|
| `status` | string | `"starting"` / `"ready"` / `"error"` |
| `service_version` | string | 服务端软件版本 |
| `model_loaded` | bool | 模型是否加载完成（继承旧设计思路） |
| `current_model` | string \| null | 当前模型名，未加载为 `null` |

- **语义**：只答「进程活着、协议通」，不承诺可识别；版本握手在本 action 完成（§5）

### 3.2 `ready` — 协议级就绪确认

- **方向**：Launcher → Service
- **请求 payload**：无
- **成功响应 payload**：`{"ready": true, "current_model": str}`
- **失败场景**：模型仍在加载 → `ok: true` 且 `"ready": false`（这是正常状态而非错误，Launcher 继续等待）；模型加载失败 → `ok: false` + `3002`
- **语义**：🔴 `Socket 可连接 ≠ 模型已就绪`。Launcher 的就绪等待必须轮询本接口，禁止固定 sleep（大纲原则 4）

### 3.3 `recognize` — 音频识别

- **方向**：Client → Service
- **请求**：JSON 头含 `audio_format` + `audio_bytes`，二进制体为原始 PCM（默认 16kHz / 单声道 / 16bit，契约库 `paths.py` 常量）
- **成功响应 payload**：

| 字段 | 类型 | 说明 |
|:---|:---|:---|
| `text` | string | 识别文本 |
| `confidence` | float \| null | 置信度（模型不给时为 `null`，禁止编造） |
| `duration_ms` | int | 音频时长 |
| `segments` | array[{`start_ms`: int, `end_ms`: int, `text`: str}] | 时间戳分段（v1.4 追加）。**引擎给不出时整个字段省略**（🔴 禁止编造）；funasr 系引擎经 `generate()` 时间戳输出获得 |
| `language` | string | 语种码（如 `"zh"`/`"en"`，v1.4 追加）。SenseVoice 元标签（`<\|zh\|>` 等）提取；其他引擎给不出则省略 |

- **失败场景**：未就绪 `2001`；音频参数非法或体长与 `audio_bytes` 不符 `4001`；推理失败 `4002`；qwen3-asr 引擎单段音频超 20 分钟（模型自身上限）→ `4001`（message 注明 `engine_limit`，🔴 禁止静默截断）

### 3.4 `model_info` — 模型查询

- **方向**：Client → Service
- **请求 payload**：无
- **成功响应 payload**：

```json
{
  "current_model": "fun-asr-nano",
  "available_models": [
    {
      "name": "fun-asr-nano",
      "loaded": true,
      "source": "model_id:FunAudioLLM/Fun-ASR-Nano-GGUF"
    },
    {
      "name": "sensevoice-small",
      "loaded": false,
      "source": "model_id:iic/SenseVoiceSmall"
    }
  ]
}
```

- **注册表载体**（服务端配置内嵌，选型二）：`available_models` 即服务端
  `config.yaml` 的 `models` 段登记项；`source` 标明加载来源（`model_id:` 缓存/在线
  或 `local_path:` 本地直载）。注册表 YAML 结构：

```yaml
# Zen_VocoType_Service/config.yaml
models:
  fun-asr-nano:
    model_id: FunAudioLLM/Fun-ASR-Nano-GGUF
    engine_type: funasr-gguf
  sensevoice-small:
    model_id: iic/SenseVoiceSmall
    vad_model_id: iic/speech_fsmn_vad_zh-cn-16k-common-pytorch
  # 本地直载条目（model_id 与 local_path 二选一）：
  # my-local-model:
  #   local_path: /绝对路径/到/模型目录
default_model: fun-asr-nano  # 必须存在于注册表，否则服务端启动报错退出
```

- **语义**：模型切换后的**交叉验证手段**——`model_switch` 返回成功后，调用方应以本接口复核（大纲 §5-4）

### 3.5 `model_switch` — 模型切换

- **方向**：Client → Service
- **请求 payload**：`{"model_name": str}`（取值必须存在于 §3.4 注册表）
- **成功响应 payload**：`{"current_model": str}`（回显切换后的真实模型名）
- **失败场景**：模型不存在 `3001`；加载失败 `3002`；切换后校验不通过 `3003`
- **语义**：🔴 服务端必须真实分发加载对应模型（旧版忽略 `model_name` 的假切换为反面案例）；切换期间并发 `recognize` / `audio_chunk` end 返回 `2002`

### 3.6 `audio_chunk` — 流式分片识别（v1.4 实现）

长音频（单段 ≥2 小时，16kHz/16bit/单声道 PCM，2h ≈ 230MB）的承载通道。
设计原则：复用现有「每请求帧必有一响应帧」的严格有序模型——**每帧的响应即天然 ack**，不引入异步推送。chunk 对象的构造/校验以契约库 `chunk.py` 为单一出处，🔴 禁止两端各自实现导致漂移。

#### 3.6.1 帧语义

`audio_chunk` 请求头在通用字段之外携带 `chunk` 对象，按 `phase` 分三阶段：

| 阶段 | `chunk` 字段 | 二进制体 | 成功响应 payload |
|:---|:---|:---|:---|
| **begin** | `{"phase": "begin", "session_id": str, "total_bytes": int（可选预告）}` + 头级 `audio_format`（同 recognize 约定） | 空 | `{"session_id": str, "max_session_bytes": int, "max_session_seconds": int}` |
| **data** | `{"phase": "data", "session_id": str, "seq": int}` + 头级 `audio_bytes` | PCM 分片（≤ `MAX_BODY_BYTES`） | `{"received_bytes": int}`（累计值，即进度反馈） |
| **end** | `{"phase": "end", "session_id": str}` | 空 | 同 `recognize` 响应 payload（§3.3 全字段） |

- `session_id` 由**客户端**在 begin 时生成（UUID 字符串，契约库 `chunk.new_session_id`），服务端校验唯一性
- `seq` 从 0 开始严格递增，服务端校验连续性，乱序/跳号/重复 → `4003`
- `total_bytes` 预告仅为服务端预校验手段（预告即超上限可 begin 阶段直接拒），缺失不报错

#### 3.6.2 会话规则

1. **单连接单活跃会话**：同一连接同时只允许一个进行中的会话；begin 时已有活跃会话 → `4003`。不同连接各自独立（会话绑定连接，🔴 禁止跨连接续传——与 MessageBuffer 每连接独立的安全约定一致）
2. **连接断开即会话销毁**：连接关闭时清理其活跃会话（临时文件删除、状态释放），🔴 禁止断连后会话残留
3. **空闲超时清理**：会话超过 `chunk_session_idle_timeout_s`（默认 120s，可配置）未收到新帧即销毁；清理时机为惰性（收到该会话的下一帧时报 `4003`）+ 周期兜底
4. **总量上限**：会话累计 PCM ≤ `chunk_session_max_bytes`（默认 256MB ≈ 2.2 小时，可配置），超限 → `4004` 并销毁会话
5. **会话 PCM 落盘**：begin 时创建会话临时 WAV 文件（XDG data 目录下 `zen_vocotype/chunk_sessions/`，🔴 不放 runtime tmpfs——tmpfs 即内存，2h WAV 230MB 会重现内存驻留问题），data 帧到达即 append，end 后删除。🔴 不做全量内存驻留
6. **互斥语义**：end 触发的识别与 `recognize` 同级——经同一推理 worker 串行执行；模型切换中收到 end → `2002`（会话保留，客户端可稍后重发 end）；未就绪 → `2001`

#### 3.6.3 校验链

未就绪（`2001`）→ 切换中（`2002`，仅 end 阶段检查）→ 会话状态（`4003`）→ 超上限（`4004`）→ 音频格式（`4001`）

#### 3.6.4 各引擎长音频策略

| 引擎 | 策略 |
|:---|:---|
| `funasr-gguf`（默认） | ✅ 长音频主力。end 触发时直接复用会话 WAV 文件喂给 CLI（跳过 PCM→float32→int16→WAV 往返） |
| `funasr`（sensevoice-small） | ✅ 支持。从会话 WAV 读回转 float32 走 `generate(batch_size_s=60)` 内部分段 |
| `qwen3-asr` | ⚠️ 维持短音频定位：单段音频超 20 分钟（模型自身上限）→ `4001`（message 注明 `engine_limit`），🔴 禁止静默截断 |

## 5. 版本握手

1. Client/Launcher 建立连接后**首个请求必须为 `health`**，比较双方 `protocol_version`
2. 兼容策略（契约库 `version.is_compatible`，单一出处）：**MAJOR.MINOR 完全一致**才兼容
3. 不兼容时：Client 必须向用户明确报错「协议版本不一致，客户端 X / 服务端 Y」并拒绝后续业务请求；🔴 禁止静默继续（大纲 §5-5）
4. 服务端收到版本不兼容的请求可返回 `1003`
5. ⚠️ v1.3 客户端连接 v1.4 服务端将被 `1003` 拒绝（严格相等语义）——四组件同仓库同批发版，不接受混合版本部署

## 6. 就绪语义与启动时序

```
Service 启动 ──► 立即监听 Socket（health 可答 starting）
              ──► 异步加载模型（后台线程）
              ──► 加载完成：health.status = ready，ready 返回 true
              ──► 加载失败：health.status = error，ready 返回 3002 及真实原因
```

- 🔴 先监听后加载（旧版「先加载模型再监听 Socket」导致冷启动 66 秒为反面案例）
- Launcher 以 `ready` 轮询等待，超时预算基于 P99 冷启动实测（阶段 3 实测标定），区分「进程已死」与「仍在启动」

## 7. 安全与健壮性约定

1. 帧头/体超上限 → 记错误日志并关闭连接（防御恶意或损坏数据）
2. 任何解析失败 → 返回 `1001`/`1004`，禁止抛异常导致连接无响应悬挂
3. 每条连接独立 MessageBuffer，禁止跨连接共享缓冲状态
4. 所有错误响应的 `message` 面向日志与排障，写真实原因，禁止空字符串或占位符
5. `segments`/`language` 引擎给不出时省略字段，🔴 禁止编造占位值

### 7.1 Socket 本地访问控制（v1 强制项）

> 语音 PCM 是敏感数据；Unix Socket 不等于安全边界。以下约束与服务端 bind 实现绑定，缺失任一项即视为实现缺陷。

1. **默认路径位于用户私有运行目录**（`$XDG_RUNTIME_DIR`，回退 `~/.local/run` 并校验目录权限 0700）；🔴 禁止默认使用全局可写 `/tmp`，/tmp 仅允许显式配置覆盖
2. **bind 前**校验目标路径非符号链接、属主为自身（防预创建/链接攻击）
3. **bind 后**显式 `chmod 0600`（不依赖进程 umask）
4. **连接接收时**以 `SO_PEERCRED` 校验对端 UID，仅允许同 UID 连接；违规拒绝并返回 `1006`（`ERR_UNAUTHORIZED_PEER`）

## 8. 超时动态化与长音频运营约定（v1.4 新增）

### 8.1 服务端推理超时链

静态常量标定必然随音频时长失准，v1.4 起统一按音频时长动态计算：

```
timeout_s = max(基础值, 音频秒数 × RTF保守值(引擎) × 安全系数)
```

- **基础值**：`infer_timeout_s`（默认 300s，兼作模型切换预算——首次切换的模型下载时间仍被覆盖）
- **RTF 保守值**：`ModelEntry.rtf_estimate`（可配置覆盖），内置标定：`funasr-gguf` 0.2（实测 0.08–0.12）、`funasr` 0.3、`qwen3-asr` 1.5
- **安全系数**：`rtf_safety_factor`（默认 2）

例：2 小时音频 + funasr-gguf → 7200 × 0.2 × 2 = 2880s（48 分钟）。

### 8.2 接入方 I/O 超时标定建议

`audio_chunk` end 响应时长 ≈ 音频时长 × RTF × 安全系数。🔴 接入方（如 AI_Video_Transcriber）必须按音频时长自行设定 end 帧的 I/O 超时，禁止沿用短音频场景的静态值（官方客户端 `RECOGNIZE_IO_TIMEOUT_S` 75s 仅覆盖 60s 录音场景，不适用于长音频）。

### 8.3 磁盘与资源

- 会话 WAV 落盘于 XDG data 目录（契约库 `paths.py` 常量 `DEFAULT_CHUNK_SESSION_DIR`），2h ≈ 230MB 磁盘占用，运行环境需保证可用空间
- 长任务独占推理 worker 期间，并发 `recognize` 按队列阈值（`queue_max_pending`）排队或 `2002` 拒绝，语义不变
