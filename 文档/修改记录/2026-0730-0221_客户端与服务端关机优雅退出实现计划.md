## 一、背景与现状盘点

### 1.1 问题

方案文档核心结论：**进程在关机流程到达「资源拆除」阶段之前自行退出，即可避免
SIGBUS/SIGSEGV 崩溃及 Apport 弹窗**。两组件当前均未在检测点 ①② 退出，关机时
只能被动等 systemd 发 SIGTERM，存在落入资源拆除区的风险（AppImage/FUSE + Qt 托盘
为高危组合）。

### 1.2 现状盘点（2026-07-30 02:21 全仓调研）

| 项 | Client | Service |
|:---|:---|:---|
| 检测点 ①（`commitDataRequest` / EndSession） | ❌ 全仓 0 匹配 | ❌ 全仓 0 匹配 |
| 检测点 ②（logind `PrepareForShutdown`） | ❌ 全仓 0 匹配 | ❌ 全仓 0 匹配 |
| SIGTERM / SIGINT 处理 | ❌ 无处理器（`README.md:145` 明示无托盘模式"退出请发 SIGTERM"，但该路径恰是无清理路径） | ✅ `main.py:211-212` 汇流 `shutdown_event` |
| 退出清理序列 | ✅ `ClientApp.shutdown()`（`app.py:222-238`：定时器→热键→录音→网络线程→托盘），挂 `aboutToQuit`（`main.py:118`） | ✅ 五段式（`main.py:233-241`：server→worker→model→锁），汇流 `shutdown_event` |
| 托盘退出路径 | ✅ `quit_requested → app.quit`（`main.py:117`） | ✅ `quit_requested → shutdown_event.set`（`main.py:118`） |
| 主循环形态 | 必有显示环境（`display_available` 探测，headless 退出码 6），`QApplication.exec()` | 双形态：托盘 `QApplication` + 200ms 轮询；headless 降级 `shutdown_event.wait()` 纯阻塞 |

**结论**：两端「退出序列」均完备可直接复用；缺口全部在「触发源」。
本计划 = 给两端各接两个检测点 + 客户端补 SIGTERM/SIGINT + 必要的幂等与形态收敛。

**不在本仓库**（全仓检索无此文件，代码侧亦确认零实现），本计划为首次落地。

## 二、方案定稿

### 2.1 检测点接入决策

| 检测点 | Client 决策 | Service 决策 |
|:---|:---|:---|
| ① 会话信号（最早退出点） | `app.commitDataRequest.connect(quit)`——Qt6 xcb 插件自动注册 GNOME 会话客户端，零额外代码 | 托盘形态同接 `commitDataRequest → shutdown_event.set()` |
| ② logind `PrepareForShutdown`（兜底） | QtDBus 监听系统总线 → `app.quit()` | QtDBus 监听系统总线 → `shutdown_event.set()`（托盘与 headless 统一） |
| ③ systemd 单元 | ❌ 不采用。两组件均可改码，①+② 已覆盖；且项目已有「GUI 应用禁用 systemd 路径」红线，不再引入单元维护面 | 同左 |
| SIGTERM / SIGINT | ✅ 新增（README 明示的退出路径必须确定性清理） | ✅ 已有，不动 |

### 2.2 检测点② 技术选型：PySide6.QtDBus（零新增依赖）

| 候选 | 结论 |
|:---|:---|
| **PySide6.QtDBus** | ✅ **采纳**。已随 PySide6 6.11.1 提供，2026-07-30 实测 `QDBusConnection.systemBus().isConnected() == True`；两端均已依赖 PySide6，零新增依赖 |
| dbus-next（方案 §3.3 示例） | ❌ 不采纳。纯 Python 但属新增依赖，能力被 QtDBus 全覆盖 |
| dasbus / GLib 系 | ❌ 不采纳。引入 GI 栈，与 Qt 技术栈混杂 |

QtDBus 收信号需要事件循环——由此引出服务端 headless 形态收敛（§4.2）。

### 2.3 统一实现形态

两端各新增一个同构小模块 `session_watch.py`：

```python
# 职责：检测点②。监听 logind PrepareForShutdown，触发 on_shutdown 回调。
# 红线：连接失败必须静默降级（仅记 warning），不得影响启动。
class SessionShutdownWatcher(QObject):
    def __init__(self, on_shutdown, parent=None): ...
    # 内部：QDBusConnection.systemBus().connect(
    #     "org.freedesktop.login1", "/org/freedesktop/login1",
    #     "org.freedesktop.login1.Manager", "PrepareForShutdown",
    #     self._slot)
    # _slot 中调用 on_shutdown()；连接返回 False 或异常 → 记 warning 后空置
```

## 三、客户端实施设计（`Zen_VocoType_Client`）

### 3.1 改动清单

| # | 位置 | 改动 |
|:--|:---|:---|
| C1 | 新增 `src/zen_vocotype_client/session_watch.py` | §2.3 watcher 实现，`on_shutdown` 回调签名 `Callable[[], None]` |
| C2 | `main.py`（`app.exec()` 之前） | ① `app.commitDataRequest.connect(lambda _session: app.quit())`<br>② 创建 `SessionShutdownWatcher(app.quit)`（随 `app` 父子关系存活）<br>③ 注册 SIGTERM/SIGINT：`signal.signal(sig, lambda *_: app.quit())` |
| C3 | `src/zen_vocotype_client/app.py::shutdown` | 增加幂等 guard（`if self._shutdown_done: return`）——托盘退出、`commitDataRequest`、logind、SIGTERM 四个触发源可能并发/重复到达 |

### 3.2 关键约束

- 🔴 信号 handler 内只做 `app.quit()`：Python 信号 handler 于主线程字节码间隙执行，
  `app.quit()` 仅投递退出事件，实际清理仍在事件循环内经 `aboutToQuit → shutdown()`
  完成，无重入风险；
- 🔴 `commitDataRequest` 处理函数禁止交互/阻塞/弹窗，不调用 `session.cancel()`（方案 §3.1 红线）；
- 🔴 watcher 创建失败（无系统总线：容器/CI）仅记 warning，启动流程不受影响（方案 §4 静默降级）；
- 清理序列（`shutdown()` 内五段）**一字不改**，本次只加触发源与幂等 guard；
- 接线顺序：C2 全部挂接须在 `client.start()` 成功之后、`app.exec()` 之前，避免启动
  失败早退路径（`main.py:112-115`）被 watcher 干扰。

## 四、服务端实施设计（`Zen_VocoType_Service`）

### 4.1 改动清单

| # | 位置 | 改动 |
|:--|:---|:---|
| S1 | 新增 `src/zen_vocotype_service/session_watch.py` | §2.3 watcher 实现，`on_shutdown = shutdown_event.set`（`threading.Event.set` 线程安全，可被 Qt 信号槽直接调用） |
| S2 | `main.py::_run_with_tray` | 托盘形态：① `app.commitDataRequest.connect(lambda _s: shutdown_event.set())`；② 创建 watcher |
| S3 | `main.py` headless 分支 | **主循环收敛**：由 `shutdown_event.wait()` 改为 `QCoreApplication` + 200ms QTimer 轮询（复用 `_run_with_tray` 的既有模式），watcher 在两种形态统一接入 |
| S4 | （顺带修复，独立提交）退出序列 | 追加 `ChunkSessionRegistry` 全局清理——调研确认的既有缺口：进程退出时活跃会话 WAV 仅靠断连钩子清理，直接退出会残留文件 |

### 4.2 headless 形态收敛说明（S3）

现状 headless 主循环是 `shutdown_event.wait()` 纯阻塞，没有 Qt 事件循环，QtDBus
信号无法投递。收敛方案：

```python
def _run_headless(ctx, shutdown_event) -> None:
    app = QCoreApplication(sys.argv)          # 🔴 QCoreApplication，非 QApplication：无显示依赖
    watcher = SessionShutdownWatcher(shutdown_event.set, app)
    timer = QTimer(); timer.timeout.connect(lambda: ...); timer.start(200)  # 轮询 shutdown_event → app.quit
    app.exec()
```

- 🔴 必须用 `QCoreApplication`（headless 下创建 `QApplication` 即崩，client 侧
  `display_available` 探测正是防此坑）；
- 收敛后托盘/headless 两形态主循环同构（Qt 事件循环 + 200ms 轮询），`_run_with_tray`
  可抽取共用轮询逻辑，减少分支；
- SIGTERM/SIGINT 既有行为不变（`signal.signal` 置位 `shutdown_event`，轮询发现后退出）；
- 🔴 无显示环境的 CI/容器：系统总线不可达时 watcher 静默降级，主循环行为与现状等价。

### 4.3 幂等性

- `shutdown_event.set()` 天然幂等，多触发源并发无害；
- 退出序列单次执行由主循环单线程保证（`main.py:233-241` 只走一遍），无需额外 guard；
- S4 的全局清理需与断连钩子/空闲清理幂等共存（重复清理同一会话不得报错）。
