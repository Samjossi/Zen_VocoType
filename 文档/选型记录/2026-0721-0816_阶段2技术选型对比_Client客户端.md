## 2. 选型一：应用线程与事件架构

> 背景：客户端同时存在四类异步源：Qt 事件循环（托盘）、pynput 热键回调线程、sounddevice 录音回调线程、Socket 网络收发。阶段 0 选 PySide6 的核心收益即信号槽跨线程安全，需定稿线程划分。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. Qt 主线程 + QThread workers + 信号槽 | 信号槽天然跨线程排队，UI 更新零手动同步；QThread 生命周期与 QCoreApplication 集成干净；根除旧 GTK `GLib.idle_add` 打补丁模式 | 需严格遵守「worker 对象 moveToThread」范式；pynput/sounddevice 自带线程不入 Qt 体系，回调内只能发信号 |
| B. Qt 主线程 + 裸 threading + Signal | 少一层 QThread 包装 | 线程退出与 Qt 对象销毁时序需手动保证，易留野指针 |
| C. asyncio 桥接（qasync） | 网络层写法现代 | 引入事件循环桥接复杂度；与 pynput/sounddevice 线程模型叠加后三类并发原语并存，调试困难 |

**推荐结论：A**。线程划分：

| 线程 | 职责 | 对外通信 |
|:---|:---|:---|
| Qt 主线程 | 托盘 UI、状态机持有、全部状态展示 | — |
| QThread（网络 worker） | Socket 长连接收发、health 探测 | `Signal` 回主线程 |
| pynput 回调线程 | 热键按下/松开原始事件 | 仅发 `Signal`，🔴 禁止直接触碰业务状态 |
| sounddevice 回调线程 | 音频块采集入队 | 仅写线程安全队列，🔴 禁止任何业务调用 |

主线程是唯一的状态机持有者：所有异步事件统一收敛为 Qt 信号进入主线程后驱动状态转移，从架构上消除竞态。

## 3. 选型二：服务端连接管理

> 背景：大纲已定「Socket 客户端长连接复用」；需定稿连接建立时机、服务端缺席行为、协议版本握手位置。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. 启动即探测 + 懒连接长连 + 失败显式报错 | 启动时 `health` 探测一次，托盘即时展示服务端状态（就绪/加载中/未运行）；识别请求时复用长连，断线自动重连一次，仍失败则按 C1 明确提示 | 实现路径最多，但每条都是直线逻辑 |
| B. 纯懒连接（首次请求才连） | 实现最少 | 托盘无法展示服务端状态；用户按住说话说完才发现服务端没开，体验差 |
| C. 每请求新建短连 | 无重连状态管理 | 每次识别付一次建连成本；与「长连接复用」既定方向冲突 |

**推荐结论：A**。细节：连接建立后立刻执行协议版本握手（协议文档 §5），版本不一致 → 断开 + 托盘红态 + 通知明确报错；长连由网络 worker（选型一）持有，收到对端关闭或写失败时置「未连接」态并通知主线程更新托盘；重连仅限一次立即尝试，🔴 禁止后台无限重试刷日志（服务端长期缺席时以托盘状态呈现，用户可经托盘菜单手动重试）。

## 4. 选型三：热键按住/松开语义实现

> 背景：交互核心是「按住说话、松开识别」。pynput 提供两种用法，语义差异关键。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. `keyboard.Listener` + 自维护组合键状态机 | press/release 原始事件齐全，可实现真正的按住/松开语义；组合键解析（`<ctrl>+``）自行实现后可做配置化校验 | 需自己跟踪修饰键按下集合（约几十行状态逻辑） |
| B. `GlobalHotKeys` | 组合键解析现成 | 🔴 语义是「组合达成时触发一次回调」，无松开事件；按住语义需 hack（回调后另起监听等释放），绕路且时序脆弱 |

**推荐结论：A**。模块内实现 `HotkeyBackend` 抽象（阶段 0 既定：为 Wayland 迁移预留 evdev/Portal 后端）+ `PynputBackend` 实现。配置项 `hotkey` 的解析在启动时校验一次，非法表达式启动即报错（🔴 禁止运行期才暴露配置错误）。防抖动：同一热键按下事件重复触发（系统键重复）时忽略，仅首次按下转移状态机。

## 5. 选型四：录音缓冲策略

> 背景：录音时长不定（按住多久录多久），需定稿 sounddevice 的使用形态与保护上限。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. `InputStream` 回调 + 线程安全队列累积 | 不定长录音的自然形态；松开即停流拼接，尾音完整；回调内零业务逻辑（选型一约束） | 需处理回调线程与消费线程的队列协议 |
| B. `RawInputStream`（bytes 直接入队） | 少一次 numpy 转换 | bytes 追加拼接大录音时是 O(n²) 风险，需额外块列表管理；收益微小 |
| C. `sd.rec` 定长 + 轮询延长 | API 最简单 | 定长假设与按住语义冲突，轮询延长等于自造 A |

**推荐结论：A**。细节：16kHz/16bit/单声道（契约库冻结常量）录制，回调将音频块放入 `queue.Queue`，录音停止时拼接为单段 PCM；最大录音时长命名常量（默认 60 秒，注明依据：对齐协议体上限 `MAX_BODY_BYTES` 留足余量），到达上限自动停止录音并进入识别流程 + 通知提示「已达最大录音时长」；设备选择默认系统默认输入设备，配置可覆盖，启动时探测并日志记录实际设备与采样率，设备缺席启动即明确报错（🔴 禁止录音时才发现）。

## 6. 选型五：状态机实现

> 背景：C7 已定状态划分；旧客户端状态散落在上帝类各方法内，转移无校验。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. 手写枚举 + 集中转移表 | 零依赖；非法转移抛异常显式暴露 bug；单测容易；与 Qt 信号直接接线 | 转移表需手写维护（五状态规模下是优点而非负担） |
| B. `transitions` 库 | 功能全（回调/条件/嵌套） | 五状态用不上其 90% 功能；与 Qt 事件流叠加后调试栈变深 |
| C. `QStateMachine` | 与 Qt 信号原生集成 | 状态机绑定 Qt 对象体系，脱离 UI 单测困难；对五状态属重型方案 |

**推荐结论：A**。转移表集中定义 `(from_state, event) → to_state`，非法转移抛 `InvalidTransition` 并记日志；状态机仅存在于主线程（选型一），`completed`/`error` 为瞬态：完成输出或提示后立即回到 `idle` 并更新托盘。

## 7. 选型六：剪贴板读写工具

> 背景：输出方案（阶段 0 选型四）要求「备份 → 写入 → 粘贴 → 校验后恢复」，工具选择影响恢复校验能力。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. Qt `QClipboard` | 已是 PySide6 一部分，零新增依赖；X11/Wayland 双栈经 Qt 抽象；`dataChanged` 信号可辅助恢复校验；支持文本与 MIME 数据 | 读写必须回 Qt 主线程（经信号槽即满足） |
| B. pyperclip | API 极简 | 本质是 xclip/xsel 子进程封装；X11 下复制后进程退出内容即失（依赖剪贴板管理器），恢复语义不可靠 |
| C. xclip/xsel 子进程直调 | 可控 | 同 B 的进程生命周期问题；额外系统依赖 |

**推荐结论：A. Qt `QClipboard` 主用**。xclip 保留为 Qt 剪贴板不可用（极端环境）时的降级路径，降级必须记 warning + 通知（C4）。

## 8. 选型七：Ctrl+V 粘贴模拟

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. pynput `Controller` 模拟 Ctrl+V | pynput 已是热键依赖，零新增；X11 下与热键监听同栈行为一致 | Wayland 下同样受限（与热键后端同命运，随后端抽象一并迁移） |
| B. xdotool key | 独立进程不占用 Python 输入状态 | 新增系统依赖；子进程调用有 ~10ms 级启动开销 |
| C. pyautogui | 跨平台 API | 底层仍是 X11 调用，功能冗余，体积与依赖不划算 |

**推荐结论：A. pynput `Controller` 主用 + B. xdotool 降级**（与阶段 0 选型四的降级链一致，降级记 warning + 通知）。

## 9. 选型八：剪贴板恢复竞态根除方案

> 背景：C3 —— 旧版「粘贴后固定 sleep 0.5s 恢复」的竞态：粘贴未完成即恢复导致输出丢失，或用户在此期间复制了新内容被覆盖。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. 内容比对 + 保守延迟恢复 | 恢复前校验剪贴板当前内容仍为本进程写入的识别文本，是则恢复原备份，否则保留用户新内容并记日志；逻辑确定、可单测 | 延迟仍是一个经验值（但已命名常量 + 可配置 + 注明依据，符合 C2） |
| B. 监听 `dataChanged` 等焦点应用取走数据 | 理论上零猜测 | 🔴 X11 剪贴板语义下「粘贴完成」无可观测事件，目标应用读取剪贴板不产生可区分信号，工程上不可靠 |
| C. 不恢复原剪贴板 | 无竞态 | 劫持用户剪贴板不还，体验不可接受 |

**推荐结论：A 为主、B 的可用部分辅助**。完整时序：备份原剪贴板 → 写入识别文本并记录指纹（文本哈希 + 写入时间戳）→ 模拟 Ctrl+V → 延迟 `paste_restore_delay_ms`（默认 500ms，配置项已存在于 `config.yaml`，依据：覆盖主流应用粘贴读取的 P99 经验值，沿用旧版数值但去除其「裸 sleep」性质）→ 恢复前比对指纹，一致则恢复、不一致则放弃恢复并记日志。若 Qt 剪贴板 `dataChanged` 信号显示内容已被第三方替换，提前跳过恢复。

## 10. 选型九：错误提示通道

> 背景：C1/C4 要求所有失败对用户可见。客户端无窗口，提示载体需选型。

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| A. 托盘 `showMessage` + 图标状态色 | 无窗口产品的原生通知位；图标颜色（灰=服务端未连接/绿=就绪/红=错误）提供常时状态；点击菜单可查看最近错误 | 依赖托盘可用；部分桌面环境 `showMessage` 样式受限 |
| B. notify-send 子进程 | 桌面原生通知，无托盘时仍可用 | 新增系统依赖（libnotify）；通知历史不可回查 |
| C. 声音提示 | 无需视觉注意力 | 单一通道无法传达错误详情，仅适合作为辅助 |

**推荐结论：A 主 + B 兜底 + C 辅助（可选配置）**。托盘不可用时（阶段 0 既定的无托盘降级模式）自动切 notify-send 并记 warning；错误分两级——瞬时错误（识别失败、服务端未就绪）走通知，持续状态（服务端断连）走图标色 + 菜单状态页，🔴 禁止同一错误通知轰炸（同类错误 5 秒内去重，命名常量）。

## 11. 推荐结论汇总

| # | 选型项 | 结论 | 关键理由 |
|:---:|:---|:---|:---|
| 1 | 线程与事件架构 | **Qt 主线程持状态机 + QThread 网络 worker + 回调线程仅发信号** | 全部竞态收敛于主线程 |
| 2 | 服务端连接管理 | **启动 health 探测 + 懒连接长连 + 失败显式报错** | 托盘可展示状态；满足 C1 |

| 4 | 录音缓冲 | **`InputStream` 回调 + 队列累积 + 60s 上限** | 不定长录音自然形态 |
| 5 | 状态机 | **手写枚举 + 集中转移表** | 零依赖；非法转移显式化 |
| 6 | 剪贴板工具 | **Qt `QClipboard`（xclip 降级）** | 零新增依赖；恢复校验可用 |
| 7 | 粘贴模拟 | **pynput `Controller`（xdotool 降级）** | 零新增依赖 |

| 9 | 错误提示 | **托盘消息+图标色主，notify-send 兜底，声音可选** | 满足 C1/C4；防通知轰炸 |
