## 1. 传输层

| 项 | 定稿 |
|:---|:---|
| 传输 | Unix Domain Socket（`SOCK_STREAM`） |
| 路径默认值 | 生产/开发均为**用户私有运行目录**下（`$XDG_RUNTIME_DIR`，回退 `~/.local/run`）：`zen_vocotype.sock` / `zen_vocotype_dev.sock`（契约库 `paths.py` 唯一出处，组件配置仅可覆盖；🔴 禁止默认使用全局可写 /tmp——可预测路径在多用户系统可被抢先 bind 冒充服务端） |
| 连接模型 | Client 长连接复用；Launcher 按需短连接（`ready` 轮询） |
| 并发 | v1 单客户端假设；服务端按连接逐一处理，同连接内请求—响应严格有序 |

## 2. 帧格式（复合帧）

```
┌────────────────────┬──────────────────────┬─────────────────────┐
│ 4 字节大端头长度 N  │ JSON 头（UTF-8，N 字节）│ 二进制体（可为空）    │
└────────────────────┴──────────────────────┴─────────────────────┘
```

- **头长度 N**：仅统计 JSON 头字节数，不含自身 4 字节、不含二进制体
- **二进制体**：长度由 JSON 头中的 `audio_bytes` 字段声明（无体时省略该字段或置 0）
- **防御性上限**：头 ≤ 64KB；体 ≤ 约 10 分钟 PCM（`frames.py` 中 `MAX_HEADER_BYTES` / `MAX_BODY_BYTES`），超限即判帧损坏，服务端记录错误并关闭连接
- **粘包处理**：沿用旧项目验证可用的 MessageBuffer 思路（持续 feed 字节流、逐帧取出），重新实现不复制

与旧协议差异：旧协议把 base64 音频内嵌 JSON（33% 体积膨胀）；复合帧头保持 JSON 可读可调试，音频走原始 PCM 体，零膨胀。

### 2.1 JSON 头字段

| 字段 | 类型 | 方向 | 必填 | 说明 |
|:---|:---|:---|:---:|:---|
| `action` | string | 双向 | ✅ | 见 §3 action 全集 |
| `protocol_version` | string | 双向 | ✅ | 协议版本号（§5 版本握手） |
| `request_id` | string | 请求方生成，响应方回显 | ✅ | 请求—响应配对；UUID 即可 |
| `ok` | bool | 响应 | ✅ | `true` 成功 / `false` 失败 |
| `error` | object | 响应 | 失败时必填 | `{"code": int, "message": str}`，错误码见 §4 |
| `audio_format` | object | 请求（含音频时） | 含音频时必填 | `{"sample_rate": 16000, "channels": 1, "sample_width": 2}` |
| `audio_bytes` | int | 请求（含音频时） | 含音频时必填 | 二进制体字节数，服务端据此校验实际收到长度 |
| `payload` | object | 双向 | 视 action | 各 action 业务字段容器（§3） |

### 2.2 响应总约定

- 成功：`"ok": true` + `payload` 携带结果
- 失败：`"ok": false` + `error.code` / `error.message`；🔴 任何失败必须显式返回错误响应，禁止超时静默、禁止占位结果（旧假模型兜底为反面案例）
- `request_id` 必须回显请求方的值

## 3. Action 全集

> 常量定义见契约库 `actions.py`；`ALL_ACTIONS` 用于服务端入站校验，未知 action 返回 `1002`。

### 3.1 `health` — 健康检查

- **方向**：Client/Launcher → Service
- **请求 payload**：无
- **成功响应 payload**：

| 字段 | 类型 | 说明 |
|:---|:---|:---|
| `status` | string | `"starting"` / `"ready"` / `"error"` |
| `service_version` | string | 服务端软件版本 |
| `model_loaded` | bool | 模型是否加载完成（继承旧设计思路） |
| `current_model` | string \| null | 当前模型名，未加载为 `null` |

- **语义**：只答「进程活着、协议通」，不承诺可识别；版本握手在本 action 完成（§5）

### 3.2 `ready` — 协议级就绪确认

- **方向**：Launcher → Service
- **请求 payload**：无
- **成功响应 payload**：`{"ready": true, "current_model": str}`
- **失败场景**：模型仍在加载 → `ok: true` 且 `"ready": false`（这是正常状态而非错误，Launcher 继续等待）；模型加载失败 → `ok: false` + `3002`
- **语义**：🔴 `Socket 可连接 ≠ 模型已就绪`。Launcher 的就绪等待必须轮询本接口，禁止固定 sleep（大纲原则 4）

### 3.3 `recognize` — 音频识别

- **方向**：Client → Service
- **请求**：JSON 头含 `audio_format` + `audio_bytes`，二进制体为原始 PCM（默认 16kHz / 单声道 / 16bit，契约库 `paths.py` 常量）
- **成功响应 payload**：

| 字段 | 类型 | 说明 |
|:---|:---|:---|
| `text` | string | 识别文本 |
| `confidence` | float \| null | 置信度（模型不给时为 `null`，禁止编造） |
| `duration_ms` | int | 音频时长 |

- **失败场景**：未就绪 `2001`；音频参数非法或体长与 `audio_bytes` 不符 `4001`；推理失败 `4002`

### 3.4 `model_info` — 模型查询

- **方向**：Client → Service
- **请求 payload**：无
- **成功响应 payload**：

```json
{
  "current_model": "paraformer-large",
  "available_models": [
    {"name": "paraformer-large", "loaded": true},
    {"name": "SenseVoiceSmall", "loaded": false}
  ]
}
```

- **语义**：模型切换后的**交叉验证手段**——`model_switch` 返回成功后，调用方应以本接口复核（大纲 §5-4）

### 3.5 `model_switch` — 模型切换

- **方向**：Client → Service
- **请求 payload**：`{"model_name": str}`
- **成功响应 payload**：`{"current_model": str}`（回显切换后的真实模型名）
- **失败场景**：模型不存在 `3001`；加载失败 `3002`；切换后校验不通过 `3003`
- **语义**：🔴 服务端必须真实分发加载对应模型（旧版忽略 `model_name` 的假切换为反面案例）；切换期间并发 `recognize` 返回 `2002`

### 3.6 `audio_chunk` — 流式分片（预留，v1 不实现）

- **帧复用说明**：流式识别未来复用同一复合帧结构——首帧声明 `audio_format`，后续帧仅带 PCM 体；本设计仅为帧格式预留该能力
- 🔴 v1 阶段任何端不得实现/发送本 action；服务端入站校验放行（`audio_chunk` 在 `ALL_ACTIONS` 中）后由分发层返回 `1005`（`ERR_ACTION_NOT_SUPPORTED`，语义区别于 `1002` 未知 action：调用方不应按「请求有误」修正重试）

## 4. 错误码表

> 常量定义见契约库 `errors.py`；区间即语义，新增错误码必须落入对应区间并同步本文档。

| 码 | 常量 | 含义 | 主要使用方 |
|---:|:---|:---|:---|
| 1001 | `ERR_MALFORMED_FRAME` | 帧格式非法（长度前缀异常、JSON 头解析失败） | Service |
| 1002 | `ERR_UNKNOWN_ACTION` | 未知 action | Service |
| 1003 | `ERR_PROTOCOL_VERSION_MISMATCH` | 协议版本不兼容 | 双向 |
| 1004 | `ERR_MISSING_FIELD` | 请求头缺必填字段 | Service |
| 1005 | `ERR_ACTION_NOT_SUPPORTED` | action 已定义但本端版本未实现（v1 的 audio_chunk） | Service |
| 1006 | `ERR_UNAUTHORIZED_PEER` | 对端身份校验失败（SO_PEERCRED UID 非白名单） | Service |
| 2001 | `ERR_NOT_READY` | 服务未就绪（模型加载中收到 recognize） | Service |
| 2002 | `ERR_BUSY` | 服务忙碌（模型切换中的并发请求） | Service |
| 3001 | `ERR_MODEL_NOT_FOUND` | 模型不在注册表 | Service |
| 3002 | `ERR_MODEL_LOAD_FAILED` | 模型加载失败 | Service |
| 3003 | `ERR_MODEL_SWITCH_FAILED` | 切换后校验不通过 | Service |
| 4001 | `ERR_INVALID_AUDIO` | 音频参数非法/体长不符 | Service |
| 4002 | `ERR_RECOGNITION_FAILED` | 推理执行失败 | Service |

## 5. 版本握手

1. Client/Launcher 建立连接后**首个请求必须为 `health`**，比较双方 `protocol_version`
2. 兼容策略（契约库 `version.is_compatible`，单一出处）：**MAJOR.MINOR 完全一致**才兼容，patch 差异放行
3. 不兼容时：Client 必须向用户明确报错「协议版本不一致，客户端 X / 服务端 Y」并拒绝后续业务请求；🔴 禁止静默继续（大纲 §5-5）
4. 服务端收到版本不兼容的请求可返回 `1003`

## 6. 就绪语义与启动时序

```
Service 启动 ──► 立即监听 Socket（health 可答 starting）
              ──► 异步加载模型（后台线程）
              ──► 加载完成：health.status = ready，ready 返回 true
              ──► 加载失败：health.status = error，ready 返回 3002 及真实原因
```

- 🔴 先监听后加载（旧版「先加载模型再监听 Socket」导致冷启动 66 秒为反面案例）
- Launcher 以 `ready` 轮询等待，超时预算基于 P99 冷启动实测（阶段 3 实测标定），区分「进程已死」与「仍在启动」

## 7. 安全与健壮性约定

1. 帧头/体超上限 → 记错误日志并关闭连接（防御恶意或损坏数据）
2. 任何解析失败 → 返回 `1001`/`1004`，禁止抛异常导致连接无响应悬挂
3. 每条连接独立 MessageBuffer，禁止跨连接共享缓冲状态
4. 所有错误响应的 `message` 面向日志与排障，写真实原因，禁止空字符串或占位符

### 7.1 Socket 本地访问控制（v1 强制项）

> 语音 PCM 是敏感数据；Unix Socket 不等于安全边界。以下约束与服务端 bind 实现绑定，缺失任一项即视为实现缺陷。

1. **默认路径位于用户私有运行目录**（`$XDG_RUNTIME_DIR`，回退 `~/.local/run` 并校验目录权限 0700）；🔴 禁止默认使用全局可写 `/tmp`，/tmp 仅允许显式配置覆盖
2. **bind 前**校验目标路径非符号链接、属主为自身（防预创建/链接攻击）
3. **bind 后**显式 `chmod 0600`（不依赖进程 umask）
4. **连接接收时**以 `SO_PEERCRED` 校验对端 UID，仅允许同 UID 连接；违规拒绝并返回 `1006`（`ERR_UNAUTHORIZED_PEER`）
