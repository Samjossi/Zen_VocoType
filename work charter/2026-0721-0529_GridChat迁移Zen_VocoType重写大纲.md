# GridChat 迁移 Zen_VocoType 重写大纲

> **状态**：草稿
> **范围**：Zen_VocoType_Service / Zen_VocoType_Client / Zen_VocoType_Launcher 三个组件的整体重写
> **时间**：2026-07-21 05:29（设计）
> **优先级**：高

---

## 1. 背景与动机

GridChat 三件套（`参考代码/GridChat_Service`、`参考代码/GridChat_Client`、`参考代码/GridChat_Launcher`）是早期开发的语音转文字软件：按住全局热键录音 → 服务端 FunASR 识别 → 文字粘贴到光标处。软件能运行，但代码组织混乱、缺陷密集，维护成本已超过重写成本。

**重写方针**：🔴 **不搬运任何旧代码文件**，仅参考其架构逻辑与踩坑经验，在 Zen_VocoType 三件套中从零实现。

### 1.1 旧项目核心问题摘要

| 组件 | 主要问题 |
|:---|:---|
| GridChat_Service | 模型切换是假的（加载逻辑硬编码 paraformer，忽略 model_name）；假模型兜底静默返回占位文本；硬编码开发者机器路径 `~/dish/models`；模型路径按 cwd 相对解析导致部署后失效；三套配置源互相矛盾；Socket 路径三处不一致；`pkill -f "python main.py"` 粗暴停服 |
| GridChat_Client | 约 30% 死代码（~1100 行本地推理遗留）；780 行上帝类内嵌托盘 UI；sys.path hack 裸导入；print 当日志；三套配置并存且 socket_config.json 无人读取；命名混乱（GridChat/VoiceGlass/EarDriv 三名混用） |
| GridChat_Launcher | 全部路径硬编码；psutil 子串匹配查进程有误报与竞态；无单实例锁；固定 sleep（0.5s/4s）拍脑袋；超时即失败、无重试无清理；返回值约定混乱导致 exit code 恒为 0；README 与代码脱节 |

### 1.2 已发生的关键事故（必须在新架构中根除）

2026-07-21 服务端冷启动超时事故：PyInstaller onefile 解压 19 秒 + 模型"在线加载"43 秒 ≈ 66 秒，超过启动器 60 秒超时预算，启动器误判失败、客户端未启动，而服务端实际在超时判定 6 秒后就绪。根因是**模型路径按 cwd 相对解析**导致随包模型从未生效 + **先加载模型再监听 Socket** 的启动顺序。

## 2. 重写原则

| # | 原则 | 说明 |
|:---:|:---|:---|
| 1 | 逻辑参考，代码重写 | 只继承架构思路、协议设计、交互模型；不复制任何旧文件 |
| 2 | 单一配置源 | 每个组件一个配置入口，禁止多套配置并存 |
| 3 | 路径自定位 | 所有路径基于程序自身目录或显式配置解析，🔴 禁止 cwd 相对路径、禁止硬编码个人机器路径 |
| 4 | 协议级就绪信号 | 组件间状态通过协议接口确认，禁止用固定 sleep 充当同步手段 |
| 5 | 失败可清理 | 任何启动/切换失败必须回收已分配资源，不留孤儿进程 |
| 6 | 文档与代码同步 | README 描述的行为必须与代码实际行为一致，变更代码必须同步文档 |
| 7 | 组件独立 | 三个组件是三个独立项目，🔴 文件夹之间禁止任何代码互相 import；协作只通过 Unix Socket 协议；每个组件均可独立启动运行 |

## 3. 目标架构

```
┌─────────────────────┐
│ Zen_VocoType_       │  启动入口：拉起服务端 → 等待协议级就绪 → 拉起客户端
│ Launcher            │  单实例锁 + PID 管理 + 失败清理
└─────────┬───────────┘
          │ 进程编排
    ┌─────┴─────┐
    ▼           ▼
┌─────────┐  Unix   ┌─────────┐
│ Service │◄─Socket─│ Client  │
│ 语音识别 │  JSON   │ 热键/录音│
│ 模型管理 │  协议   │ 托盘/输出│
└─────────┘         └─────────┘
```

### 3.1 组件职责

| 组件 | 职责 | 明确不负责 |
|:---|:---|:---|
| **Zen_VocoType_Service** | FunASR 模型加载与推理；模型下载/切换/校验；Unix Socket 服务；服务状态上报 | 不录音、不与用户直接交互 |
| **Zen_VocoType_Client** | 全局热键监听；音频录制；识别请求发送；结果文字输出（剪贴板+粘贴）；用户交互界面 | 不加载模型、不做推理 |
| **Zen_VocoType_Launcher** | 按序拉起服务端与客户端；就绪等待；冲突检测（单实例锁）；失败清理与进程回收 | 不参与运行时业务，拉起后即退出或驻留（待定） |

**独立运行行为**（三组件互不引用代码，各自可单独启动）：

| 组件 | 单独启动时的行为 |
|:---|:---|
| Service | 正常启动并监听 Socket，等待连接；自身功能完整，不依赖任何其他组件 |
| Client | 正常启动（热键/托盘可用）；识别请求时若连不上服务端，明确提示「服务端未运行」，🔴 禁止崩溃或静默失败 |
| Launcher | 正常执行编排流程；某端缺失时报错并给出明确提示 |

### 3.2 通信协议（继承旧设计，做两处改进）

- **协议契约库**：根目录新增**独立的第四组件** `Zen_VocoType_Protocol/`（协议契约库），存放帧格式、action 常量、错误码，拥有独立的 `pyproject.toml`。Service 与 Client 以**包依赖方式**引用（开发时 `pip install -e`），打包时随各自产物内嵌——🔴 禁止三组件文件夹之间任何形式的相对路径 import；协议库与三端是「库—使用方」关系，不构成组件间互相引用。🔴 同时禁止回到旧 GridChat 两端各定义一份协议的做法（易漂移）
- **传输**：Unix Domain Socket（`SOCK_STREAM`），路径由配置统一定义，🔴 禁止多处写死
- **帧格式**：`[4 字节大端长度前缀][UTF-8 JSON 载荷]` + MessageBuffer 粘包处理 —— 旧实现经验证可用，直接沿用设计
- **改进一**：音频不再 base64 内嵌 JSON（旧设计有 33% 体积膨胀），改为二进制帧或独立数据通道（设计阶段定稿）
- **改进二**：新增协议级**就绪/状态接口**（旧 `health` 已含 `model_loaded` 字段的思路），语义区分「Socket 可连接」与「模型已就绪」

### 3.3 开发调试形态

单项目（monorepo）多目录结构，客户端与服务端同仓库、同 `.venv`，支持两端同时调试。**同仓库不等于耦合**：三组件各自为独立 Python 项目（各自入口、各自配置），文件夹之间无任何代码引用，唯一共享物是协议契约库 `Zen_VocoType_Protocol/`（以 editable install 方式装入同一 venv）：

| 场景 | 形态 |
|:---|:---|
| 生产部署 | 服务端、客户端各自打包成独立程序，由 Launcher 拉起为两个独立进程 |
| 开发调试 | 两个终端 / IDE 复合调试配置（VSCode `compounds`）同时跑两端，可同链路断点 |

- **Launcher 开发模式**：`--dev` 参数下不拉二进制，改用当前 `.venv` 的 `python main.py` 拉起两端
- **dev 环境隔离**：开发调试使用独立 Socket 路径（如 `/tmp/zen_vocotype_dev.sock`），避免与正式版互相干扰（继承旧 `start_dev_debug.sh` 的思路）

### 3.4 Action 规划（初稿）

| action | 方向 | 说明 |
|:---|:---|:---|
| `health` | Client/Launcher → Service | 返回服务状态、版本、模型是否就绪 |
| `ready` | Launcher → Service | 协议级就绪确认（就绪=模型加载完成，可识别） |
| `recognize` | Client → Service | 音频识别，返回文本/置信度/时长 |
| `model_info` | Client → Service | 当前模型与可用模型列表 |
| `model_switch` | Client → Service | 切换模型（服务端必须真实分发到对应模型，🔴 禁止旧版假切换） |

### 3.5 资产（图标）迁移

图标等资源文件不属于代码，🔴「不搬运旧代码」方针**不适用于资产**——旧图标可直接复制迁移，但需统一重命名、统一存放、统一加载方式。

**旧项目资产盘点**：

| 旧位置 | 内容 | 迁移去向 |
|:---|:---|:---|
| `GridChat_Service/asset/icon_{32,64,128,256}.png`、`icon.png` | 服务端托盘图标 | `Zen_VocoType_Service/assets/` |
| `GridChat_Client/assets/grid_chat_icon_{32,64,128,256}.png` | 客户端托盘图标 | `Zen_VocoType_Client/assets/` |
| `GridChat_Launcher/asset/star_{32,64,128,256}.png` | 启动器通知/桌面图标 | `Zen_VocoType_Launcher/assets/` |
| `GridChat_Client/grid_chat.desktop` | 桌面入口（引用图标） | 阶段 4 重写为 Zen_VocoType 版 |

**迁移约束**：

1. 统一重命名为 `zen_vocotype_*` 命名（如 `zen_vocotype_service_icon_64.png`），🔴 禁止残留 `grid_chat` / `star` 等旧名
2. 各组件资产放各自 `assets/` 目录，随包分发
3. 加载一律走「程序自身目录」解析 helper（兼容开发环境与 PyInstaller `_MEIPASS`），🔴 禁止相对 cwd——旧 Launcher 的 `asset/star_64.png` 相对路径在 AppImage 中静默失效即为反面案例
4. 托盘/通知/.desktop 三处用图在各阶段交付时同步接入（见 §6 各阶段交付物）
5. 如需新设计品牌图标，在阶段 0 提出；未定稿前先用迁移的旧图标占位

## 5. 必须根除的旧缺陷（新架构硬性约束）

| # | 旧缺陷 | 新架构约束 |
|:---:|:---|:---|
| 1 | 模型路径按 cwd 相对解析，随包模型失效 | 路径一律基于程序自身目录 / 显式配置；打包后必须实测验证 |
| 2 | 先加载模型再监听 Socket，冷启动 66 秒 | 先监听 Socket、异步加载模型，`ready` 接口报告真实就绪状态 |
| 3 | 启动器超时即失败、无重试无清理 | 超时预算基于 P99 冷启动实测；区分「进程已死」与「仍在启动」；失败回收已拉起的子进程 |
| 4 | 模型切换是摆设（忽略 model_name） | 模型注册表驱动加载分发，切换后 `model_info` 必须可验证 |
| 5 | 假模型静默返回占位文本 | 🔴 禁止任何静默降级；模型不可用时必须显式报错 |
| 6 | `pkill -f "python main.py"` 粗暴停服 | PID 文件 + 精确匹配；Launcher 统一管理子进程生命周期 |
| 7 | psutil 子串匹配查进程 | 可执行路径精确匹配 + Launcher 单实例锁文件 |
| 8 | 固定 sleep（0.5s/2s/4s/60s/180s 魔法数字） | 全部改为条件等待；常量集中命名并注明依据 |
| 9 | 三套配置源、Socket 路径三处不一致、协议两端各定义一份 | 每组件单一配置源；Socket 路径全局唯一出处；协议集中于共享包 `Zen_VocoType_Protocol/` |
| 10 | 30% 死代码、上帝类、sys.path hack、print 日志 | 标准包结构 + logging；热键/录音/转录/输出/托盘拆为独立模块 |
| 11 | 打包 onefile 3.4GB、启动解压 19 秒 | 打包方案重新选型（onedir 优先），启动耗时纳入验收 |
| 12 | exit code 不反映启动器成败 | 所有入口正确返回退出码 |
| 13 | 图标路径相对 cwd，AppImage 打包后静默失效（降级为 None 不报错） | 资源路径统一经「程序自身目录」解析 helper（兼容 PyInstaller `_MEIPASS`）；图标缺失必须记 warning |
| 14 | —（新增约束，对应重写原则 7） | 三组件文件夹之间禁止任何代码互相 import；唯一共享物为协议契约库（包依赖方式接入）；每组件可独立启动、独立打包、独立交付 |

## 6. 迁移阶段规划

> 每阶段完成后产出验收记录，通过后方进入下一阶段。

### 阶段 0 — 设计定稿
- 交付物：通信协议设计文档（帧格式、action 全集、错误码）；**协议契约库 `Zen_VocoType_Protocol/` 的模块划分与接入方式（editable install）**；三组件目录结构与配置方案（各自独立 `pyproject.toml`）；客户端 UI 技术选型结论；**资产迁移清单与重命名方案（含是否新设计品牌图标的结论）**
- 依赖：本大纲审阅通过

### 阶段 1 — Zen_VocoType_Service
- 交付物：Socket 服务 + 协议层；模型注册表驱动的加载/切换；先监听后异步加载模型；`health`/`ready`/`recognize`/`model_info`/`model_switch` 全 action；PID 文件管理；logging
- 验收标准：冷启动 Socket 可连接时间 ≤ 5 秒（模型异步加载）；模型切换真实生效且可验证；无 cwd 相对路径

### 阶段 2 — Zen_VocoType_Client
- 交付物：热键监听、录音、Socket 客户端（长连接复用）、文字输出（剪贴板+粘贴+恢复）、状态机、托盘/UI、单一配置；**客户端托盘图标迁移接入（`assets/`，自定位路径加载）**
- 验收标准：按住说话→松开出字全流程可用；服务端未就绪时给出明确提示而非静默失败；托盘图标在开发与打包环境下均正常显示

### 阶段 3 — Zen_VocoType_Launcher
- 交付物：按序拉起、协议级就绪等待、单实例锁、冲突检测、失败清理、正确 exit code、notify-send 状态通知（**含通知图标迁移接入**）；**`--dev` 开发模式（用 `.venv` 直接拉起两端源码 + dev 独立 Socket 路径隔离）**
- 验收标准：双击桌面入口一次成功拉起全套；重复执行幂等；模拟服务端慢启动/崩溃场景下行为正确（不误判、不留孤儿进程）；`--dev` 模式与正式模式行为一致、互不干扰

### 阶段 4 — 打包与端到端
- 交付物：三组件打包方案与产物（**资产随包分发，打包后图标实测可见**）；`.desktop` 桌面入口（**引用迁移后的图标**）；端到端验收报告
- 验收标准：打包后冷启动全流程一次成功；总启动耗时较旧版（66 秒+）显著下降并有实测数据；托盘/通知/桌面入口图标在打包环境下全部正常显示

## 7. 验收总标准

1. 🟢 全流程：按住热键 → 说话 → 松开 → 文字出现在光标处，打包后实测通过
2. 🟢 启动：Launcher 单次执行拉起全套，P99 冷启动在超时预算内；重复执行幂等
3. 🟢 模型：切换真实生效，`model_info` 可交叉验证；无任何静默降级路径
4. 🟢 配置：每组件单一配置源；全局无 cwd 相对路径、无个人机器路径
5. 🟢 资产：图标全部迁移并重命名为 `zen_vocotype_*`；开发/打包两种环境下托盘、通知、.desktop 图标均正常显示
6. 🟢 独立：三组件文件夹之间零代码引用（可静态检查验证）；每个组件可单独启动、单独打包、单独交付；Client 在服务端缺席时明确报错而非崩溃
7. 🟢 代码：无死代码；logging 完备；三组件 README 与实际行为一致
