## 1. 现象与影响

| 项 | 内容 |
|:---|:---|
| 现象 | 新版客户端全部自动化测试（106 项）全绿，但**手动按物理热键 `<ctrl>+<alt>+o` 从不触发录音**；托盘无蓝点、GNOME 顶栏无红色麦克风、日志无任何状态转移 |
| 对照 | 模拟按键注入的测试与复现实验全部正常；直接用 `Recorder` 类录音一切正常 |
| 影响 | 客户端核心交互（按住说话）在真实使用下完全不可用；测试通过给了「已完成」的错误信心 |
| 根因 | `_canonical_key` 用 `(vk, char)` 元组比较主键：配置解析端的 `'o'` 是 `KeyCode(vk=None, char='o')`，而**物理按键事件携带物理键码** `KeyCode(vk=32, char='o')`——元组永不相等，物理事件的主键匹配永远失败 |
| 修复 | char 非空按 char 匹配、char 为空（特殊键）按 vk 匹配（提交 `604395b`） |

## 2. 技术根因详解

### 2.1 pynput 按键对象的三种表示

pynput 中「同一个键」在不同来源下是**不同构的对象**：

| 来源 | 字符键（如 o） | 特殊键（如 F9） |
|:---|:---|:---|
| 配置解析 `HotKey.parse("<ctrl>+<alt>+o")` | `KeyCode(vk=None, char='o')` | `KeyCode(vk=65478, char=None)` |
| 物理按键事件（X11 Listener） | `KeyCode(vk=32, char='o')` **带物理键码** | `Key.f9`（枚举，`.value` 为同 vk 的 KeyCode） |
| XTest 模拟注入事件 | `KeyCode(vk=None, char='o')`（与解析端同构） | 同解析端 |

关键不对称：**字符键的 vk 在物理事件中非空、在解析/注入中为空**；特殊键则靠 vk 才能跨枚举/KeyCode 统一。

### 2.2 缺陷代码（修复前）

```python
def _canonical_key(key) -> tuple:
    if isinstance(key, keyboard.Key):
        key = key.value
    return (getattr(key, "vk", None), getattr(key, "char", None))  # ← 元组整体比较
```

- 解析端 `'o'` → `(None, 'o')`
- 物理事件 `'o'` → `(32, 'o')`
- `(None, 'o') != (32, 'o')` → **物理按键永不匹配**

而全部测试使用的合成事件是 `KeyCode.from_char("o")` → `(None, 'o')`，与解析端**天然同构**——测试数据与生产数据不同分布，测试全绿成为假象。

### 2.3 历史成因

该函数本是修 F9 配对问题（`HotKey.parse("<f9>")` 产出 `KeyCode(vk=65478)`，Listener 事件传来 `Key.f9` 枚举）时引入的：当时发现「只比 char 不行」（F9 无 char），改为 `(vk, char)` 元组——解决了特殊键，却**对字符键引入了 vk 敏感性**。两个方向的正确规则是互斥的，必须分类处理。

### 2.4 修复（提交 `604395b`）

```python
def _canonical_key(key) -> tuple:
    if isinstance(key, keyboard.Key):
        key = key.value
    char = getattr(key, "char", None)
    if char is not None:
        return ("char", char)   # 字符键：只按 char（忽略 vk 有无）
    return ("vk", getattr(key, "vk", None))  # 特殊键：按 vk（统一枚举与 KeyCode）
```

- 字符键：解析端/物理/注入三方 `("char", 'o')` 全一致 ✓
- 特殊键：解析端 `("vk", 65478)` = 事件端 `("vk", 65478)` ✓（F9 案例不回退）

### 2.5 事实核查：pynput 内建相等语义与旧版参照（修复后补查）

修复后回查发现，**正确逻辑早已存在于两处，本次属于重造轮子且造错了方向**：

**① pynput 内建 `KeyCode.__eq__` 就是「char 优先」语义**（实测）：

```python
KeyCode.from_char('o') == KeyCode(vk=32, char='o')   # True（char 同则等，vk 不参与）
KeyCode(vk=1, char='o') == KeyCode(vk=32, char='o')  # True（vk 不同 char 同仍等）
KeyCode.from_char('o') == KeyCode.from_char('x')     # False
```

即修复后手写的分类匹配规则，**就是库内建的相等行为**——`_canonical_key` 本质是重造 `KeyCode.__eq__`。

**② 旧版 `参考代码/GridChat_Client/src/hotkey_manager.py` 的匹配策略天然正确**：

```python
self._key_map = {'ctrl': keyboard.Key.ctrl_l, '`': keyboard.KeyCode.from_char('`'), ...}
self._pressed.add(key)                   # 直接存事件对象
all(k in self._pressed for k in keys)    # set 成员判定——依赖 pynput 内建 __eq__
```

旧版从不做字段级比较，直接用对象相等判定（set 成员），因此物理事件带不带 vk 都天然匹配，**从未踩到这个坑**。

**③ 远路归因与公允边界**：

- **错处**：动手实现匹配逻辑前，没有先查库内建相等语义、也没有逐行对照旧版已验证的判定方式；大纲「逻辑参考、代码重写」被执行为「凭理解重写」。正确顺序应是：先穷尽库内建能力 → 对照旧版验证过的方式 → 再补旧版缺失的语义
- **方向没错**：旧版匹配自身有两个缺陷，恰是选型三要求自维护状态机的原因——a) 无去抖（系统键重复会反复触发 `on_press`，旧版靠业务层 `if not self.recording` 兜底）；b) release 语义为「任意键松开即结束」（`not all(...)`，先松修饰键就停录），与定稿的「主键释放为准」不同。自研状态机方向正确，错在实现路径

## 4. 为什么测试没有抓住它（测试盲区分析）

1. **合成事件与生产事件不同构**：T2.5 单测用 `KeyCode.from_char("o")`（vk=None）构造合成事件——与配置解析端对象同构，天然匹配。物理事件的 vk=32 从未进入测试数据集
2. **F9 修复的副作用无回归覆盖**：修特殊键时引入 `(vk, char)` 元组，字符键路径没有「带 vk 的物理形态」用例
3. **注入式集成测试的隐蔽偏差**：所有「端到端」验证（ClientApp 复现、E2E 测试钩子）的事件来源要么同构合成、要么 XTest 注入（字符键无 vk 甚至丢失），没有一条路径经过真实物理事件形态
4. **教训总结**：**「测试全绿」只在「测试数据分布 = 生产数据分布」时成立**。涉及 OS 输入设备（键盘/音频/剪贴板）的代码，合成数据必须按生产事件的完整字段复刻，且至少保留一条真实物理路径的人工验证项

## 6. 附录：相关知识备查

### 6.1 X11 keysym 对照（本机实测）

| 键 | keysym | pynput 事件对象 |
|:---|:---:|:---|
| 左 Ctrl | 65507 (0xFFE3) | `Key.ctrl`（通用枚举，非 `ctrl_l`） |
| 左 Alt | 65513 (0xFFE9) | `Key.alt`（通用枚举） |
| 字符 o | keycode 32 | `KeyCode(vk=32, char='o')`（物理）/ `KeyCode(vk=None, char='o')`（注入/解析） |
| F9 | 65478 | `Key.f9` 枚举（物理）/ `KeyCode(vk=65478)`（解析） |

### 6.2 XTest 注入的局限（本机实测）

- 修饰键（固定 keycode）：XTest 注入对 XRecord 监听者**可见**
- 字符键：pynput 经「临时重映射空闲 keycode」合成，**XRecord 不可见（事件丢失）**；同进程注入时 Controller/Listener 共享 X 连接上下文故可见——跨进程模拟按键**不可作为**热键类应用的验证手段
- 可靠的非物理注入路径：`/dev/uinput`（内核级输入设备事件，需权限）——本机未配置，未实测

### 6.3 GNOME 麦克风隐私指示

- GNOME Shell 42+ 监听 PipeWire 活跃麦克风捕获流，顶栏系统状态区自动显示红色麦克风；应用无法直接控制其显隐/位置/样式
- 本机实测：sounddevice（ALSA hostapi → pipewire-alsa 路由）录音流对 PipeWire 可见（`wpctl` 中 `input_MONO [active]`），指示约 1 秒内出现；停止即消失
- KDE 另有样式、最小化 WM 无此指示——应用自有指示（悬浮窗）仍不可替代
