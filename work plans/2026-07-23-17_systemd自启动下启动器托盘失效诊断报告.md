# systemd 自启动下启动器「托盘不显示 + 两条启动通知」诊断报告

## 0. 结论速览

**K 老师的诊断成立，源码可逐行闭环。** 但有一处细节需修正：两条通知**不是**
service/client 两个组件各自发的，而是 **Launcher 自身在 CLI 回退路径上发的**
「正在启动…」+「启动完成…」两条。

| 症状 | 根因（源码定位） | 性质 |
|---|---|---|
| ① 重启后托盘不显示 | systemd 用户服务启动时图形会话尚未就绪，环境无 `DISPLAY`/`WAYLAND_DISPLAY` → Launcher `display_available()` 探测失败 → 抛 `TrayUnavailableError` → 回退一次性 CLI 模式（编排完即退出，托盘从未创建） | **机制性必然，非缺陷**（headless 保护设计正确触发了） |
| ② 弹出两条「启动成功」消息 | CLI 回退路径的编排器经 `notify-send` 发「正在启动语音输入服务…」（拉起 Service 时）+「启动完成，可以开始语音输入（总耗时 X 秒）」（就绪后）。systemd 用户服务**有 D-Bus 会话总线**（通知可达桌面）但**无显示环境**（托盘不可达）——两者通道独立，故「通知能弹、托盘没有」 | 设计行为 |
| ③ （隐患）客户端大概率已崩溃 | Client `main.py` **没有** DISPLAY 探测（Service/Launcher 都有），无显示环境下 `QApplication()` 直接 Qt 硬崩（SIGABRT）；编排器只在拉起瞬间查一次存活（AppImage FUSE 引导需数秒，检查时必然活着），就绪等待只看 Service——**客户端死后 Launcher 仍报「启动完成」** | **代码缺口**（建议修复，见 §4.2） |

**「为什么 gridchat 没问题」也属实**：gridchat 走 GNOME autostart
（`~/.config/autostart/`），桌面环境在图形会话完全建立后才执行，DISPLAY 天然
齐备；systemd 用户服务随 `default.target` 启动，早于 gnome-session 经
`systemctl --user import-environment` 导入 DISPLAY 的时刻——这是两条自启动
路径的本质差异，非本项目代码差异。

## 1. 证据链（源码逐行）

### 1.1 日志原文与代码一一对应

用户日志行：

```
7月 23 16:55:56 ... 托盘模式不可用（无 DISPLAY/WAYLAND_DISPLAY 显示环境），回退一次性 CLI 模式
```

对应代码链路（三步，全部命中）：

1. **探测**：[`app.py:69-72`](../../Zen_VocoType_Launcher/src/zen_vocotype_launcher/app.py)
   `display_available()` 只检查两个环境变量：
   ```python
   return bool(os.environ.get("DISPLAY") or os.environ.get("WAYLAND_DISPLAY"))
   ```
2. **抛错**：[`app.py:130-132`](../../Zen_VocoType_Launcher/src/zen_vocotype_launcher/app.py)
   ```python
   if not display_available():
       raise TrayUnavailableError("无 DISPLAY/WAYLAND_DISPLAY 显示环境")
   ```
   （注释明确这是防御：headless 下 Qt 可能 SIGABRT 硬崩，必须先探测后创建）
3. **回退**：[`main.py:116-120`](../../Zen_VocoType_Launcher/main.py)
   ```python
   except Exception as exc:
       logger.warning("托盘模式不可用（{}），回退一次性 CLI 模式", exc)
       return _run_cli(settings, dev_mode=False, log_file=log_file)
   ```
   → 日志措辞与实机日志**逐字吻合**。

### 1.2 两条通知的来源（修正 K 老师细节）

CLI 回退后走完整编排 [`orchestrator.py:run()`](../../Zen_VocoType_Launcher/src/zen_vocotype_launcher/orchestrator.py)，
通知仅有两处出口：

| 时机 | 代码 | 文案 |
|---|---|---|
| 拉起 Service 前 | `orchestrator.py:168` → `notify.py:59-61` | 「正在启动语音输入服务…」 |
| 就绪判定通过后 | `orchestrator.py:266` → `notify.py:63-65` | 「启动完成，可以开始语音输入（总耗时 X.X 秒）」 |

两条均以标题 `Zen_VocoType`（`notify.py:23`）经 `notify-send` 发出——即用户
看到的「两个消息」。**Service 在 headless 下不发任何通知**
（[`Service/main.py:101-103`](../../Zen_VocoType_Service/main.py) 直接降级纯
控制台，托盘对象根本不创建）；Client 若未崩，其通知走自身托盘 showMessage，
无托盘时才会兜底 notify-send（`client/tray/notifier.py:56-64`）——均非本次
两条消息的来源。

**为什么通知能弹、托盘不能显示**：通知走 D-Bus 会话总线
（`DBUS_SESSION_BUS_ADDRESS`，systemd 用户服务默认继承）；托盘走 X11/Wayland
（`DISPLAY`/`WAYLAND_DISPLAY`，图形会话建立后才导入 systemd 用户环境）。两条
通道独立，systemd 场景恰好「有前者、无后者」。

### 1.3 症状完整时序

```
登录 → systemd 用户管理器启动 default.target（gnome-session 尚未导入 DISPLAY）
  → zen_vocotype.service 拉起 Launcher AppImage
  → display_available() = False → TrayUnavailableError
  → 回退 CLI 编排：notify「正在启动…」→ 拉起 Service（headless 降级，无托盘）
    → 拉起 Client（继承无 DISPLAY 环境，见 §1.4）
    → 就绪等待仅判定 Service → notify「启动完成…」→ Launcher 退出
  ⇒ 用户视角：两条通知、零托盘图标
```

### 1.4 附带发现：Client 缺 DISPLAY 探测（隐患）

- 三组件中 Service（`main.py:101`）与 Launcher（`app.py:72`）均有显示环境
  探测，**唯独 Client 没有**：
  [`Client/main.py:80-84`](../../Zen_VocoType_Client/main.py) 无条件执行
  `QApplication(sys.argv)`。无显示环境下 Qt6 找不到 xcb 平台插件，进程
  **abort 硬崩**（非 Python 异常，无法被捕获降级）。
- 子进程环境：prod 模式 [`targets.py:158-171`](../../Zen_VocoType_Launcher/src/zen_vocotype_launcher/targets.py)
  `_prod_target` 不设 `env`，[`processes.py:107`](../../Zen_VocoType_Launcher/src/zen_vocotype_launcher/processes.py)
  `env=None` 即**继承 Launcher 环境**——Launcher 无 DISPLAY，Client 同样无。
- 漏检原因：编排器对 Client 的存活检查只有拉起后**一瞬间**的
  `is_alive()`（`orchestrator.py:220`），AppImage FUSE 引导需数秒，此刻必然
  活着；随后的就绪等待只探 Service Socket。Client 在引导完成后 Qt 崩溃，
  **无人察觉**，「启动完成」照发。

> 用户可在实机验证：`~/.local/state/zen_vocotype/logs/child_client.log`
> 尾部应有 Qt 的 `could not load the Qt platform plugin "xcb"` 报错
> （每次拉起重写该日志，见 `processes.py:102`）。此路径在项目目录外，
> 按 AGENTS.md 约束本报告不越界读取。

## 2. K 老师方案评估：改用 GNOME Autostart —— 正确，采纳

K 老师给出的三步（禁用 systemd 服务 → 写 `~/.config/autostart/zen_vocotype.desktop`
→ 重启验证）方向**完全正确**，与本项目机制吻合：

- GNOME autostart 条目在图形会话就绪后执行，DISPLAY/WAYLAND_DISPLAY 齐备 →
  `display_available()` 为 True → 走托盘模式正常路径；
- 这与 15:10 报告 §3.3 的建议一致（`tools/desktop_entry.py` 增加
  `--autostart` 选项属同一方案的产品化）。

**两处执行注意**：

1. **Exec 路径大小写**：K 老师示例写的
   `Exec=~/AppImages/zen_vocotype_launcher.Appimage` 需与实机文件
   **逐字符核对**（Linux 大小写敏感；`dist/` 官方产物命名为
   `Zen_VocoType_Launcher.AppImage`，用户目录现存为小写命名）。 Exec 指向
   不存在的文件时桌面环境**静默失败**，与 15:10 报告候选失效点 #2 同款。
2. **预期效果校准**：迁移成功后，Launcher 托盘只会**短暂出现**（编排成功
   后按 `auto_exit_delay_s` 倒计时自退，选型七「拉起确认后即退出」设计）；
   **常驻托盘是 Service 与 Client 的图标**——三者均正常出现即全量恢复。
   「等托盘正常后只发一次通知」的说法不准确：托盘模式下编排成功路径
   **不发** notify-send（通知通道是 CLI 路径专属），届时应**一条通知都没有**，
   改为看托盘图标。

## 3. 对「为什么这次新的不能启动」的直接回答

不是新 AppImage 坏了——16:55 日志证明它被 systemd 服务**成功执行**了，编排
也成功了（通知为证）。坏的是**自启动载体**：systemd 用户服务的启动时刻早于
图形会话环境注入， Launcher 的 headless 保护（15:10 报告已验证其设计正确性）
按预期触发回退。同一 AppImage 在已登录桌面里双击执行，托盘完全正常。

## 4. 处置建议

### 4.1 立即可做（用户操作，零代码，即 K 老师方案）

按 §2 三步迁移至 GNOME autostart，注意核对 Exec 路径大小写。

### 4.2 代码侧缺口修复（如需立项，另出计划）

| 优先级 | 项 | 说明 |
|---|---|---|
| P1 | **Client 补 DISPLAY 探测** | 对齐 Service/Launcher 同款保护：无显示环境时记 error 日志 + 退出非零（如 6），禁止 Qt 裸崩。`Client/main.py:80` 前加探测即可，模式照抄 `Service/main.py:101-103` |
| P2 | 编排器增强 Client 存活判定 | 拉起后延迟复查（如 3~5 秒后再 `is_alive()` 一次），或就绪等待期并发监测 Client 进程——堵住「Client 秒崩仍报启动完成」的误报窗口（`orchestrator.py:220-225` 现状） |
| P3 | `tools/desktop_entry.py` 增加 `--autostart` | 15:10 报告 §3.3 已列，本次事故证明该需求真实存在；产品化后可免用户手写桌面文件 |

### 4.3 不建议的方向

- **不建议**给 systemd 服务打补丁续命（如 `ExecStartPost=systemctl --user
  import-environment` 时序 hack 或服务里写死 `Environment=DISPLAY=:0`）——
  硬编码显示号在多会话/Wayland 下脆弱，且违背 15:10 报告已确立的「桌面
  自启动走 autostart」选型方向；
- **不建议**给 Launcher 加「无 DISPLAY 时轮询等待显示环境」——systemd
  场景下等待时长不可控，autostart 迁移后该需求消失。
