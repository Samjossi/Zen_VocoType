#: 窗口内死亡判定 CLIENT_FAILED（修复「AppImage 引导数秒后 Qt 崩溃仍报
#: 启动完成」误报——systemd 无显示环境实机事故）。默认 10 秒：FUSE 挂载 +

**改动 2**：[`orchestrator.py`](../../Zen_VocoType_Launcher/src/zen_vocotype_launcher/orchestrator.py)
就绪等待成功后、`notify_done` 之前插入存活确认：

```python
# --------------------------------- Client 存活确认（T42）
# 仅本进程拉起的 Client：AppImage 引导数秒后才初始化 Qt，拉起瞬间
# 存活不代表引导后存活（headless Qt 硬崩实机事故）；
# 轮次制循环（非 wall-clock）——经 deps.sleep 注入，测试零真实等待
if client_proc is not None and settings.client_settle_timeout_s > 0:
    steps = math.ceil(settings.client_settle_timeout_s / _SETTLE_POLL_S)
    for _ in range(steps):
        if not client_proc.is_alive():
            detail = _exit_info(client_proc, plan.client.log_path)
            logger.error("客户端拉起后存活确认期内死亡：{}", detail)
            _status(deps, f"客户端存活确认失败：{detail}")
            notifier.notify_failed(
                f"客户端拉起后退出（{detail}）", str(deps.log_file)
            )
            return ExitCode.CLIENT_FAILED  # ExitStack 回收 service（若 owned）
        deps.sleep(_SETTLE_POLL_S)
```

（`_SETTLE_POLL_S = 0.2` 模块常量；就绪等待耗时常远超 10 秒窗口，届时首轮
`is_alive()` 即终检，**零附加等待**；只有「Client 新拉起 + Service 秒就绪」
组合才会实际补等，而那正是需要观察的场景。）

**改动 3**：[`exit_codes.py`](../../Zen_VocoType_Launcher/src/zen_vocotype_launcher/exit_codes.py)
`CLIENT_FAILED` 注释扩写：`客户端拉起失败（含拉起后立即退出、T42 存活确认
窗口内死亡）`。

## 5. 风险与缓解

| 风险 | 缓解 |
|---|---|
| T42 拖慢「Client 新拉起 + Service 已在运行」场景的就绪回报（补等至多 settle 秒） | 这正是设计意图（用 10 秒换「启动完成」通知的真实性）；冷启动与全幂等两条主路径**零附加等待**（就绪等待耗尽窗口 / 跳过确认）；字段可配 0 关闭 |
| T42 误杀慢启动 Client（窗口内 Qt 尚未初始化完但进程活着） | 检查的是**进程存活**而非就绪状态，进程活着即通过——Qt 初始化慢不构成误判；只有进程真死才判失败 |
| T41 探测误伤合法 headless 用法（如 `--screenshot` selftest） | 探测放在 `--screenshot` 分支**之后**，开发工具路径不触探测；测试固化 |
| T41 新退出码 6 与既有文档/脚本冲突 | Client 现有退出码 0/2/3/4/5，6 空缺；全仓 grep 确认无脚本依赖 Client 退出码数值；README 同步 |
| T43 用户误以为 `--autostart` 替代 systemd 服务后需手工清理旧服务 | 文档「开机自启动」节明确：若曾手工配置 systemd 用户服务，须先 `systemctl --user disable --now <单元>` 再装 autostart 条目（防双启动——Launcher 有单实例锁兜底不会双跑，但会多发一条「已在运行」通知） |
| T43 autostart 条目 Exec 指向的 AppImage 被移动/改名后静默失效（15:10 报告候选失效点 #2） | 条目安装自 `install_desktop.py --dir` 的实参目录，与菜单条目同源同路径；文档注明「移动 AppImage 后需重跑安装脚本」；属 .desktop 机制固有限制 |
| XDG_CONFIG_HOME 非常规布局（自定义 config 根） | 遵循 XDG 规范读取环境变量，测试固化该路径 |

**实机验证清单**（步骤 9，用户手工执行）：

1. T41：SSH/无显示会话执行 `zen_vocotype_client.appimage` → 退出码 6 +
   error 日志，**无** Qt 崩溃栈；
2. T42：临时将 Client 位置指向一个「拉起后 3 秒自行退出」的假二进制 →
   Launcher 报「启动失败：客户端拉起后退出」+ 退出码 4（替代原误报成功）；
3. T43：`install_desktop.py --dir ~/AppImages --autostart` → 重启 →
   三托盘出现（Launcher 短暂）+ **零桌面通知**；
4. T43 对称：`uninstall_desktop.py` → 两类条目与图标清除。

## 6. 待审阅确认点

1. **T42 窗口默认值 10 秒**：依据为 AppImage 引导 + Qt 初始化实测数秒；
   若评审倾向更保守（覆盖机械硬盘冷机），可升 15 秒——代价仅为
   「Client 新拉起 + Service 秒就绪」组合的就绪回报延迟。
2. **T41 退出码取 6**：Client 未像 Launcher 那样建 `ExitCode` 枚举（现状
   为 docstring 约定字面量），本计划沿用现状只加一行 docstring；若评审
   希望顺势建枚举，属扩大范围，建议另立任务。
3. **T43 autostart 不默认安装**：保持 `--autostart` 显式启用（本计划方案）
   vs 安装即默认带自启动——本计划取前者（自启动改变登录行为，须用户
   明示；与诊断报告 §3.3 原建议一致）。
4. **T42 失败文案**：通知文案「客户端拉起后退出（{detail}）」复用既有
   `notify_failed` 通道与格式；若评审认为需与「拉起后立即退出」文案
   区分（引导后崩溃），可微调为「客户端启动后异常退出」——语义相同，
   仅措辞。
